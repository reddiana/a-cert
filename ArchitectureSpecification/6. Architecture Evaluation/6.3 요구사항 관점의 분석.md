### 6.3.1 기능 요구사항(FR) 및 시스템 기능(SF) 관점 분석

4가지 기능 요구사항과 5가지 시스템 기능이 아키텍처에 구현된 방식과 충족 결과는 다음과 같습니다.

| Req ID | 시스템 기능 | 요구사항 정의 | 구현 아키텍처 메커니즘 | 충족성 판정 |
| :---: | :---: | :--- | :--- | :---: |
| **FR-01** | **SF-02** | **중복 실행 방지 분산 락** | `LockStateMachine`에서 `ReentrantLock` 기반 원자적 임계 구역 제어와 `ConcurrentHashMap` 인메모리 락 상태를 관리함. `DistributedLockExecutor`를 통해 스케줄 실행 전 락 획득을 강제하여 다중 노드/스레드 간 중복 실행 오작동율 0%를 달성함. | **우수 (충족)** |
| **FR-02** | **SF-03** | **작업 누락 방지 분산 큐** | `QueueStateMachine`에서 `LinkedBlockingQueue`를 기반으로 원자적 인출(`poll`)을 수행하여 다중 워커 노드가 경합하더라도 단일 작업은 오직 하나의 워커에만 할당되도록 보장함. 인메모리 FIFO 처리로 작업 유실 및 중복을 방지함. | **우수 (충족)** |
| **FR-03** | **SF-04** | **저널 복구를 통한 무유실 보장** | `JournalStateMachine`과 `LocalWalStorage`를 통해 태스크 실행 상태(`PENDING`, `RUNNING`, `COMPLETED`, `FAILED`)를 로컬 디스크 및 Raft Log에 순차 기록함. 스케줄러 노드 크래시 발생 시 신규 리더가 `recoverUnfinishedTasks()`를 즉시 호출하여 `RUNNING` 상태의 미완료 작업을 10초 이내에 자동 재스케줄링함. | **우수 (충족)** |
| **FR-04** | **SF-01<br>SF-05** | **클러스터 멤버십 자가 치유 및 자동 리더 선출** | `RaftNode`와 `ClusterMembership`에서 50ms 틱 기반 하트비트 감시를 수행하여 일반 노드 장애 시 3초 이내에 멤버십에서 제외함. 리더 노드 다운 시 선출 타임아웃(800ms~1050ms) 경과 즉시 신규 선출을 개시하여 과반수(Quorum) 합의를 통해 3초 이내에 신규 리더를 선출함. | **우수 (충족)** |

### 6.3.2 비기능 요구사항(NR) 및 품질 속성 시나리오(QAS) 관점 분석

품질 속성 6대 분류(일관성, 성능, 가용성, 신뢰성, 효율성, 이식성/운용성) 및 DB 장애 내구성 요구사항에 대한 충족 분석 결과는 다음과 같습니다.

```
+-----------------------------------------------------------------------------------------+
|                  품질 속성 시나리오(QAS) 및 비기능 요구사항(NR) 충족 분석 요약                 |
|                                                                                         |
|  [일관성 / 정합성] ──► QAS-01 (100건 동시 DAG 정합성 0% 오류), QAS-03 (Split-Brain 차단)   |
|  [성능 / 저지연]   ──► QAS-02 (200건 큐 인출 0.5초 이내, 개별 지연 20ms 이하)               |
|  [가용성 / 복원력] ──► QAS-04 (팔로워 3초 자가치유), QAS-05 (리더 3초 페일오버)              |
|  [신뢰성 / 무유실] ──► QAS-06 (스케줄러 다운 시 10초 이내 미완료 태스크 100% 무유실 복구)      |
|  [자원 효율성]     ──► QAS-07 (추가 JVM 힙 점유 50MB 이하, GC STW 1초 이내)                  |
|  [이식성 / 운용성] ──► QAS-08 (외부 미들웨어 0개, 2분 이내 자동 구성), NR-07, NR-08          |
|  [DB 장애 내구성]  ──► QAS-09, NR-09 (DB 단절 중 무중단 락/큐 운영, 복구 후 30초 내 정합성 복원)|
+-----------------------------------------------------------------------------------------+
```

#### 1. 일관성 (Consistency) - `QAS-01`, `QAS-03`, `NR-02`
* **아키텍처 대응**: `LockStateMachine`의 인메모리 원자적 상호 배제와 Raft Quorum 투표 알고리즘(`(N/2)+1`)을 적용함.
* **분석 결과**: 
  - 동시 100개 요청 경합 상황에서도 후행 작업(Task B)의 중복 발화 없이 1회만 발화(`RunCount=1`)됨을 검증함 (`TC-QAS-01`).
  - 네트워크가 1:2로 분할되는 Split-Brain 상황에서 소수파 격리 노드는 Quorum 미달로 리더가 되지 못하며 전체 활성 리더 수는 1개 이하로 안정 유지됨 (`TC-QAS-03`).

#### 2. 성능 (Performance) - `QAS-02`, `NR-02`, `NR-06`
* **아키텍처 대응**: RDBMS 트랜잭션 락(`FOR UPDATE`) 대신 In-Memory `LinkedBlockingQueue` 및 `LockStateMachine`을 직접 참조하는 In-Process 처리 방식을 채택함.
* **분석 결과**: 
  - 12개 워커 스레드가 200건의 배치 대기열을 인출할 때 평균 인출 지연 20ms 이하, 최대 지연 50ms 이하, 전체 200건 인출 0.5초 이내 완료 목표를 달성함 (`TC-QAS-02`).

#### 3. 가용성 (Availability) - `QAS-04`, `QAS-05`, `NR-04`
* **아키텍처 대응**: `RaftNode`의 50ms 주기 하트비트 스케줄러, 2초 하트비트 타임아웃 판정, 노드 식별자 기반 선출 타임아웃 지터(Staggering)를 적용함.
* **분석 결과**: 
  - 일반 멤버(Follower) 노드 크래시 시 3초 이내에 활성 멤버 목록에서 제외하여 자가 치유를 완료함 (`TC-QAS-04`).
  - 활성 리더 노드 크래시 시 잔여 노드가 신속하게 리더 부재를 감지하고 3초 이내에 신규 리더를 선출하여 서비스 공백을 최소화함 (`TC-QAS-05`).

#### 4. 신뢰성 (Reliability) - `QAS-06`, `FR-03`, `NR-05`
* **아키텍처 대응**: `fsync` 기반 로컬 WAL 영속화와 `JournalStateMachine.recoverUnfinishedTasks()` 연계를 통해 태스크 상태 변경 이력을 추적함.
* **분석 결과**: 
  - 5개 태스크가 `RUNNING` 상태인 상황에서 리더 노드가 강제 종료되더라도, 신규 리더가 10초 이내에 미완료 태스크 5건을 모두 식별하여 재스케줄링을 완료하며 유실 건수 0건을 달성함 (`TC-QAS-06`).

#### 5. 효율성 (Efficiency) - `QAS-07`, `NR-06`
* **아키텍처 대응**: 별도 사이드카 프로세스나 외부 JVM 데몬 없이 기존 애플리케이션 JVM 힙 내에서 구동되는 In-Process 임베디드 라이브러리 구조를 채택함.
* **분석 결과**: 
  - 엔진 구동 전후 추가 Heap 메모리 점유량이 50MB 이하로 제어되며, 누적 GC Stop-the-World 지연 시간이 1초 이내로 유지됨 (`TC-QAS-07`).

#### 6. 이식성 및 운용성 (Portability & Operability) - `QAS-08`, `NR-01`, `NR-03`, `NR-07`, `NR-08`
* **아키텍처 대응**: Zookeeper, Redis 등 외부 분산 미들웨어 의존성을 전면 배제하고, Spring Boot Auto-Configuration 표준 패키징 및 JDK 17 표준 소켓을 기반으로 구현함.
* **분석 결과**: 
  - 외부 데몬 설치(0분) 없이 단일 JAR 의존성 추가 및 YAML 설정만으로 2분 이내에 클러스터 구성 및 정상 준비 상태가 완료됨 (`TC-QAS-08`).

#### 7. DB 장애 내구성 (Database Outage Resilience) - `QAS-09`, `NR-09`
* **아키텍처 대응**: 리더 선출(DD-01), 분산 락(DD-02), 분산 큐(DD-03), 저널링(DD-04)이 메타 DB 없이 In-Memory FSM 및 로컬 WAL만으로 완결되도록 설계하고, `ReconciliationManager`를 통한 비동기 Write-Behind 복원 파이프라인을 구축함.
* **분석 결과**: 
  - DB 연결이 물리적으로 차단된 상태에서도 50건의 분산 락/큐 오퍼레이션이 0초 중단(성공률 100%)으로 처리됨.
  - DB 복구 감지 후 30초 이내에 누적된 오프라인 저널 엔트리가 RDBMS 테이블로 유실 없이 동기화 완료됨 (`TC-QAS-09`).
