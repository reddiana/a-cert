#### 1. 일관성 (Consistency) - `QAS-01`, `QAS-03`, `NR-02`
* **아키텍처 대응**: 결정론적 Lock/Queue FSM, 커밋 후 apply 결과만 반환하는 선반영 금지 원칙, Raft Quorum(`(N/2)+1`) 커밋 규칙, 로그 최신성 투표 검사, Check-Quorum 기반 리더 자진 강등을 적용함.
* **설계 충족 근거**:
  - 어느 노드로 유입된 요청이든 리더의 단일 Raft 로그 순서로 직렬화되어 `LockStateMachine`에 apply되므로, 동시 100건의 상태 전이 경합에서도 임계 구역에는 한 번에 하나의 요청만 진입하고 후행 작업 발화는 1회로 제한됨. 임계 구역은 메타 DB가 아닌 로컬 Multi-FSM 조회로 판정하므로(5.3.2 Scenario 1) 개별 판정 지연을 10ms 이하로 유지할 수 있음.
  - 1:2 네트워크 분할 시 소수파 리더는 과반수 응답을 받지 못해 커밋·인출이 불가능하고 Election Timeout 이내에 Check-Quorum으로 강등되며, 다수파만 신규 리더를 선출할 수 있으므로 커밋 가능한 리더는 항상 1개 이하임. 복구 시 소수파의 미커밋 엔트리는 로그 불일치 절단으로 제거되어 로그가 재수렴함 (5.3.2 Scenario 5).
* **검증 연계**: `TC-QAS-01`(동시 100건 락 경합), `TC-QAS-03`(리더 소수파 격리), `TC-K8S-01`·`TC-K8S-01B`(3개 Pod 동시 100건 상태 전이), `TC-K8S-03`(Chaos Mesh 네트워크 분할), `TC-K8S-11`(부하 중 롤링 업데이트), `TC-K8S-12`(지연·패킷 손실)

#### 2. 성능 (Performance) - `QAS-02`, `NR-02`
* **아키텍처 대응**: RDBMS 트랜잭션 락(`FOR UPDATE`) 대신 In-Process 인메모리 FSM을 사용하고, 동시 명령을 Group Commit(1회 `fsync`·일괄 AppendEntries)으로 처리하며, 노드 쌍별 영속 TCP 연결로 복제 지연을 최소화함.
* **설계 충족 근거**:
  - 인출 경로에 DB 왕복이 없고, 동시 인출 요청은 Group Commit(복제 스레드가 제안 신호마다 누적 엔트리를 1회 `fsync`하고 AppendEntries 1회에 최대 256건씩 전송)으로 묶여 요청 수만큼 `fsync`·복제가 반복되지 않으므로, 개별 인출 지연 평균 20ms·최대 50ms 이하와 200건 전체 0.5초 이내 목표를 만족하도록 설계함 (5.3.2 공통 런타임 규약).
* **검증 연계**: `TC-QAS-02`(3노드 12개 워커의 200건 동시 인출), `TC-K8S-02`(3개 Pod 12개 워커의 200건 동시 인출)

#### 3. 가용성 (Availability) - `QAS-04`, `QAS-05`, `NR-04`
* **아키텍처 대응**: 250ms Heartbeat, 팔로워 응답 기반 2초 장애 판정과 `MEMBER_STATUS` 커밋, Election Timeout 1,500~2,000ms 난수, Split Vote 시 150~300ms 난수 대기 후 재선출, PreVote로 고립 노드의 term 인플레이션 방지, 신규 리더 `NO_OP` 커밋을 적용함.
* **설계 충족 근거**:
  - **팔로워 장애 (`QAS-04`)**: 마지막 AppendResponse 후 2,000ms(Heartbeat 8회 누락)에 DEAD로 판정하고, `MEMBER_STATUS(DEAD)`를 과반수 커밋·동기화하는 1초 예산을 더해 총 3초 이내에 활성 멤버십에서 제외함. 판정 임계치 2초는 GC STW(최대 1초, `QAS-07`)보다 길어 정상 노드 오탐을 배제함.
  - **리더 장애 (`QAS-05`)**: Election Timeout 상한 2,000ms로 감지 단계 2초 이내, 이후 PreVote·RequestVote 왕복과 `NO_OP` 커밋은 별도 대기 없이 수행되어 선출 단계 1초 이내를 확보하여 총 3초 이내에 서비스를 재개함. 생존 노드들이 동시에 출마해 Split Vote가 발생하면, 경쟁 후보의 거절을 받은 뒤 150~300ms 난수 대기 후 PreVote부터 재시도하여 재선출이 Election Timeout만큼 늦어지지 않도록 함. 거절 없이 응답만 없는 경우에는 Election Timeout을 유지하여 고지연 환경의 선출 반복을 방지함 (5.3.2 공통 런타임 규약 6, Scenario 2·3).
* **검증 연계**: `TC-QAS-04`(Follower Crash), `TC-QAS-05`(Leader Crash), `TC-K8S-04`·`TC-K8S-05`(컨테이너 강제 종료), `TC-K8S-11`(롤링 업데이트 중 리더 교체)

#### 4. 신뢰성 (Reliability) - `QAS-06`, `FR-03`
* **아키텍처 대응**: `fsync` 기반 로컬 WAL 영속화, Raft Log 복제, `RecoveryCoordinator`의 추적 노드 생존·Execution Target 상태 기반 복구, leaseToken 펜싱을 연계함.
* **설계 충족 근거**:
  - 작업 상태는 과반수 노드의 WAL에 커밋된 후에만 확정되므로 단일 노드 크래시로 저널이 유실되지 않음. 신규 리더 승격 후 `RecoveryCoordinator`가 DEAD 노드가 추적하던 작업만 골라 Target 상태에 따라 `REQUEUED`(NOT_FOUND·FAILED·UNKNOWN), `ADOPTED`(RUNNING, 재실행 없음), `COMPLETED`로 처리하고, 생존 노드가 추적 중인 작업은 조치하지 않아 중복 실행을 방지함. 승격(3초) 후 10초 이내 복구 예산으로 설계함 (5.3.2 Scenario 2).
  - 재기동 노드는 WAL Replay로 FSM을 복원한 뒤 로그를 따라잡아 멤버십에 재합류함 (5.3.2 Scenario 3).
* **검증 연계**: `TC-QAS-06`(추적 리더 크래시 후 고립 작업 복구), `RaftSafetyTest.restartedNodeRecoversFromWalAndRejoins`, `TC-K8S-06`(실제 K8s Job 상태 기반 고립 작업 복구), `TC-K8S-10`(Pod 재생성 후 동일 PVC의 WAL 복원·재합류)

#### 5. 효율성 (Efficiency) - `QAS-07`, `NR-06`
* **아키텍처 대응**: 별도 사이드카 프로세스나 외부 JVM 데몬 없이 기존 애플리케이션 JVM 힙 내에서 구동되는 In-Process 임베디드 라이브러리 구조를 채택하고, JPA 등 불필요한 의존성 없이 JDBC만 선택적으로 사용함.
* **설계 충족 근거**:
  - In-Memory Multi-FSM 상태를 Lock FSM(1MB) + Queue FSM(20MB) + Journal FSM(20MB) = 약 41MB로 산정하여 추가 Heap 50MB 이하 요건 내에 두고, 프로세스 간 통신(IPC)을 제거함 (5.4 용량 산정).
  - 단, 로그 압축(Snapshot/Compaction) 미구현으로 운영 부하에서는 인메모리 로그 사본이 일 약 40~70MB씩 누적되므로, 장기 무중단 운영 전 로그 압축 구현이 필요함 (5.4.2-4, `RISK-01`).
  - 엔진 추가 CPU 사용률(`NR-06`, 5% 미만)은 5.3.1 스레드 모델의 주기 작업(초당 약 100회 기동, 회당 0.1ms 가정, 안전율 2배)으로 약 0.02 Core로 산정하여, 스케줄러 전용 VM 최소 규격(4 vCPU) 대비 약 0.5%임. 회당 CPU 시간을 가정의 10배로 두어도 2.5%로 상한 이내이며, 실제 사용률은 운영 환경 컨테이너 메트릭으로 확인함 (5.4.2-4, 7.1.5).
* **검증 연계**: `TC-QAS-07`(1노드 기동·1,000건 적재 후 Heap·GC 측정), `TC-K8S-07`(엔진 비활성 기준선 Pod 대비 Heap·컨테이너 메모리), CPU 사용률은 운영 환경 컨테이너 메트릭 (7.1.5)

#### 6. 이식성 및 운용성 (Portability & Operability) - `QAS-08`, `NR-01`, `NR-03`, `NR-07`, `NR-08`
* **아키텍처 대응**: Zookeeper, Redis 등 외부 분산 미들웨어 의존성을 전면 배제하고, Spring Boot Auto-Configuration 표준 패키징, JDK 17 표준 소켓, 5.4 매니페스트 환경변수(`RAFT_NODE_ID`, `RAFT_PEERS`, `RAFT_AUTH_TOKEN`, `WAL_DATA_DIR`) 기반 자동 구성을 적용함. 피어 설정 누락 시 단일 노드 기동을 거부(Fail-fast)하여 Split-Brain을 방지함.
* **설계 충족 근거**:
  - 클러스터 구성에 필요한 사전 미들웨어가 없으므로 미들웨어 설치 시간은 0분이며, StatefulSet `Parallel` 기동과 Headless Service(`publishNotReadyAddresses`)로 피어가 동시에 서로를 발견한 뒤 리더 선출(수 초)을 거쳐 Readiness에 도달하므로 신규 노드 배포 후 2분 이내 가입 목표를 만족함 (5.4.2).
* **검증 연계**: `TC-QAS-08`(실제 TCP 소켓 3노드 부트스트랩), `TC-K8S-08`(5.4.2 매니페스트 기반 StatefulSet 신규 배포)

#### 7. DB 장애 내구성 (Database Outage Resilience) - `QAS-09`, `NR-09`
* **아키텍처 대응**: 리더 선출(DD-01), 분산 락(DD-02), 분산 큐(DD-03), 저널링(DD-04)이 메타 DB 없이 In-Memory FSM 및 로컬 WAL만으로 완결되도록 설계하고, 리더의 `WriteBehindSynchronizer`가 DB 동기화 체크포인트를 기준으로 커밋 구간을 반영(이력·체크포인트 단일 트랜잭션, log_index 멱등)하는 비동기 Write-Behind 복원 파이프라인을 구축함.
* **설계 충족 근거**:
  - 락·큐·저널 요청의 처리 경로(WAL `fsync` → Quorum 복제 → 커밋 → apply)에 DB I/O가 없고, Readiness Probe에 DB Health를 포함하지 않으므로 DB 장애 중에도 처리 중단 시간은 0초임.
  - DB 장애 중에는 WAL 압축 하한선이 DB 체크포인트에 고정되어 미반영 구간이 보존되며, 재시도 backoff 상한(10초)으로 복구를 감지한 뒤 체크포인트부터 500건 단위로 재생하므로 30초 이내에 누락·중복 없이 동기화함 (5.3.2 Scenario 4).
* **검증 연계**: `TC-QAS-09`(DB 단절 중 락·큐 수행 후 복구 동기화), `TC-K8S-09`(메타 DB Pod 중단 중 락·큐 수행 후 복구 동기화)

#### 8. 호환성 (Compatibility) - `NR-05`
* **아키텍처 대응**: `api.DistributedLockExecutor`가 AS-IS Hazelcast 공통모듈과 같은 클래스명과 `execute(lockName, logStr, Supplier|Runnable)` 시그니처를 제공하고, 자동 구성 Bean으로 등록되어 기존 주입 코드를 그대로 사용할 수 있게 함 (5.2.3).
* **설계 충족 근거**:
  - AS-IS `IMap.lock()`의 락 의미인 호출 스레드 단위 소유, 획득할 때까지 대기, 같은 스레드 재진입을 소유자 식별자 `{nodeId}:{threadId}:{ownerId}`, 기본 대기 `WAIT_FOREVER`, 스레드별 재진입 깊이 관리로 제공하므로, 두 번째 인자에 고정 문자열을 넘기거나 중첩 호출하는 기존 코드도 같은 상호 배제 결과를 얻음.
  - 수요처 변경은 import 경로, 빌드 의존성, 클러스터 설정 교체로 한정됨. 대기 중 인터럽트 시 예외 발생, 과반수 노드 장애 시 60초 후 `ClusterUnavailableException` 발생은 AS-IS와 다른 동작이므로 5.2.3에 명시하여 전환 시 점검하도록 함.
* **검증 연계**: `DistributedLockExecutorTest`(AS-IS 테스트 절차 이식, 같은 두 번째 인자를 넘기는 스레드 간 상호 배제, 같은 스레드 재진입, 5초 초과 임계 구역 뒤 대기자 획득)
