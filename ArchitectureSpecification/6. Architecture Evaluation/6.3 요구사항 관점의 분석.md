### 6.3.2 비기능 요구사항(NR) 및 품질 속성 시나리오(QAS) 관점 분석

품질 속성 6대 분류(일관성, 성능, 가용성, 신뢰성, 효율성, 이식성/운용성) 및 DB 장애 내구성 요구사항에 대한 충족 분석 결과는 다음과 같습니다.

```
+-----------------------------------------------------------------------------------------+
|                  품질 속성 시나리오(QAS) 및 비기능 요구사항(NR) 충족 분석 요약                 |
|                                                                                         |
|  [일관성 / 정합성] ──► QAS-01 (100건 동시 DAG 발화 1회, 65ms), QAS-03 (소수파 인출 0건)     |
|  [성능 / 저지연]   ──► QAS-02 (200건 인출 23ms, 평균 1.29ms·최대 8ms)                      |
|  [가용성 / 복원력] ──► QAS-04 (팔로워 제외 2,104ms), QAS-05 (리더 페일오버 1,813ms)          |
|  [신뢰성 / 무유실] ──► QAS-06 (고립 작업 복구 2,515ms, 유실 0건, 생존 노드 작업 미조치)       |
|  [자원 효율성]     ──► QAS-07 (추가 Heap 0MB, GC 9ms) ※ 장기 운영 전 로그 압축 필요         |
|  [이식성 / 운용성] ──► QAS-08 (외부 미들웨어 0개, TCP 3노드 Readiness 1,809ms)             |
|  [DB 장애 내구성]  ──► QAS-09, NR-09 (DB 단절 중 50/50건 성공, 복구 후 252건 954ms 동기화)  |
+-----------------------------------------------------------------------------------------+
```

#### 1. 일관성 (Consistency) - `QAS-01`, `QAS-03`, `NR-02`
* **아키텍처 대응**: 결정론적 Lock/Queue FSM, 커밋 후 apply 결과만 반환하는 선반영 금지 원칙, Raft Quorum(`(N/2)+1`) 커밋 규칙, 로그 최신성 투표 검사, Check-Quorum 기반 리더 자진 강등을 적용함.
* **분석 결과**:
  - 3개 노드로 분산 유입된 동시 100개 요청 경합 상황에서 100건 모두 순차 획득하고 후행 작업(Task B)은 1회만 발화함을 검증함 (`TC-QAS-01`, 전체 65ms).
  - 현재 리더를 1:2 네트워크 분할의 소수파로 격리했을 때 소수파의 큐 인출은 커밋되지 않아 거부되고, 구 리더는 Check-Quorum으로 강등되며, 다수파 신규 리더 선출 후 네트워크 복구 시 3노드 로그가 일치하도록 재수렴함 (`TC-QAS-03`).

#### 2. 성능 (Performance) - `QAS-02`, `NR-02`, `NR-06`
* **아키텍처 대응**: RDBMS 트랜잭션 락(`FOR UPDATE`) 대신 In-Process 인메모리 FSM을 사용하고, 동시 명령을 Group Commit(1회 `fsync`·일괄 AppendEntries)으로 처리하며, 노드 쌍별 영속 TCP 연결로 복제 지연을 최소화함.
* **분석 결과**:
  - 3개 노드의 12개 워커 스레드가 200건의 배치 대기열을 인출할 때 전체 23ms, 평균 인출 지연 1.29ms, 최대 8ms로 목표(0.5초, 평균 20ms, 최대 50ms)를 충족함 (`TC-QAS-02`).

#### 3. 가용성 (Availability) - `QAS-04`, `QAS-05`, `NR-04`
* **아키텍처 대응**: 500ms Heartbeat, 팔로워 응답 기반 2초 장애 판정과 `MEMBER_STATUS` 커밋, Election Timeout 1,500~2,000ms 난수, PreVote로 고립 노드의 term 인플레이션 방지, 신규 리더 `NO_OP` 커밋을 적용함.
* **분석 결과**:
  - 일반 멤버(Follower) 노드 크래시 시 2,104ms에 활성 멤버십에서 제외하여 자가 치유를 완료하고, 정상 노드는 오탐 없이 유지됨 (`TC-QAS-04`).
  - 활성 리더 노드 크래시 시 1,813ms에 신규 리더가 `NO_OP`을 커밋하여 서비스를 재개함 (`TC-QAS-05`).

#### 4. 신뢰성 (Reliability) - `QAS-06`, `FR-03`, `NR-05`
* **아키텍처 대응**: `fsync` 기반 로컬 WAL 영속화, Raft Log 복제, `RecoveryCoordinator`의 추적 노드 생존·Execution Target 상태 기반 복구, leaseToken 펜싱을 연계함.
* **분석 결과**:
  - 리더 노드가 추적하던 5개 `RUNNING` 작업에 대해 크래시 후 2,515ms에 재적재 3건, 재실행 없는 추적 인수 1건, 완료 확정 1건을 커밋하고, 생존 노드가 추적 중인 작업은 조치하지 않으며, 11개 작업 모두 추적되어 유실 0건을 달성함 (`TC-QAS-06`).
  - 재기동 노드는 WAL Replay로 FSM을 복원한 뒤 로그를 따라잡아 멤버십에 재합류함 (`RaftSafetyTest`).

#### 5. 효율성 (Efficiency) - `QAS-07`, `NR-06`
* **아키텍처 대응**: 별도 사이드카 프로세스나 외부 JVM 데몬 없이 기존 애플리케이션 JVM 힙 내에서 구동되는 In-Process 임베디드 라이브러리 구조를 채택하고, JPA 등 불필요한 의존성 없이 JDBC만 선택적으로 사용함.
* **분석 결과**:
  - 1노드 엔진 기동 및 작업 1,000건 적재 후 추가 Heap 점유량 0MB, GC 9ms로 목표(50MB, 1초)를 충족함 (`TC-QAS-07`).
  - 단, 로그 압축(Snapshot/Compaction) 미구현으로 운영 부하에서는 인메모리 로그 사본이 일 약 40~70MB씩 누적되므로, 장기 무중단 운영 전 로그 압축 구현이 필요함 (5.4.2-4, `RISK-01`).

#### 6. 이식성 및 운용성 (Portability & Operability) - `QAS-08`, `NR-01`, `NR-03`, `NR-07`, `NR-08`
* **아키텍처 대응**: Zookeeper, Redis 등 외부 분산 미들웨어 의존성을 전면 배제하고, Spring Boot Auto-Configuration 표준 패키징, JDK 17 표준 소켓, 5.4 매니페스트 환경변수(`RAFT_NODE_ID`, `RAFT_PEERS`, `RAFT_AUTH_TOKEN`, `WAL_DATA_DIR`) 기반 자동 구성을 적용함. 피어 설정 누락 시 단일 노드 기동을 거부(Fail-fast)하여 Split-Brain을 방지함.
* **분석 결과**:
  - 외부 프로세스 0개로 실제 TCP 소켓 3노드 클러스터가 1,809ms에 단일 리더 선출 및 전 노드 Readiness에 도달하고, 소켓 경로로 명령이 복제됨 (`TC-QAS-08`).

#### 7. DB 장애 내구성 (Database Outage Resilience) - `QAS-09`, `NR-09`
* **아키텍처 대응**: 리더 선출(DD-01), 분산 락(DD-02), 분산 큐(DD-03), 저널링(DD-04)이 메타 DB 없이 In-Memory FSM 및 로컬 WAL만으로 완결되도록 설계하고, 리더의 `WriteBehindSynchronizer`가 DB 동기화 체크포인트를 기준으로 커밋 구간을 반영(이력·체크포인트 단일 트랜잭션, log_index 멱등)하는 비동기 Write-Behind 복원 파이프라인을 구축함.
* **분석 결과**:
  - DB 연결이 차단된 상태에서도 50건의 락 획득·적재·인출·ACK·해제가 모두 성공(50/50)하고 노드 Readiness가 유지됨.
  - DB 복구 후 252건의 누적 이력이 954ms에 동기화되어 미동기화 0건, DB 체크포인트와 동기화 기준점이 일치함 (`TC-QAS-09`).
