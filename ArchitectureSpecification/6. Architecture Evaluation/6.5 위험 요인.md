본 절은 ATAM 방법론에 기반하여 본 분산 배치 클러스터링 아키텍처 도입 및 운영 시 발생 가능한 잠재적 **위험 요인(Risks)** 과 이에 대한 구체적인 완화 전략(Mitigation Strategies), 그리고 아키텍처 설계를 통해 안전성이 입증된 **비위험 요인(Non-Risks)** 을 정의합니다.

### 6.5.1 아키텍처 위험 요인 및 완화 전략 (Architecture Risks & Mitigation)

| :-----: | :------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-: | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RISK-01 | 로그 압축 미구현 상태의 WAL·Heap 누적 및 메타 DB 장기 장애 시 용량 소진 위험 | 현재 구현은 Snapshot/로그 압축이 없어 WAL 파일과 인메모리 로그 사본이 계속 누적되며(운영 부하 기준 WAL 약 40MB/일, Heap 약 40~70MB/일), 재기동 시 전체 WAL Replay 시간도 증가함. 압축 도입 후에도 메타 DB 장기 장애 중에는 DB 체크포인트 이전 구간만 압축할 수 있어 WAL 누적이 가속될 수 있음 (`ASM-05`). |  상  | - **로그 압축 구현(필수 선행 과제)**: FSM Snapshot 생성 후 `min(snapshotIndex, DB 체크포인트)` 이전 WAL 구간을 정리하고, 뒤처진 노드에는 `InstallSnapshot`으로 상태를 전송함 (5.3.2 공통 런타임 규약 불변식 8).<br>- **전용 PVC 용량 사전 산정**: StatefulSet `volumeClaimTemplates`로 노드당 10GiB RWO 스토리지를 할당함 (압축 미구현 시 약 250일 보존).<br>- **메모리 버퍼 비증가 구조**: Write-Behind는 별도 메모리 큐 없이 커밋된 WAL 구간을 인덱스로 직접 판독하므로 DB 장애 중 동기화 버퍼가 증가하지 않음.<br>- **운영 경보**: PVC 사용률 70%, Heap 80% 초과 경보와 압축 도입 전 계획된 초기화 절차를 수립함 (5.4.2-5 모니터링). |
| RISK-02 | 리더 노드 시스템 시계 급변(step)에 따른 lease 조기 만료 위험 | 노드 간 시계 차이는 리더 교체 시 lease 재설정으로 만료 판정에 영향을 주지 않으나, 현재 리더 노드의 시스템 시계가 운영 중 앞으로 크게 조정(step)되면 해당 리더가 기록·판정하는 lease가 조정 폭만큼 짧아짐. lease의 1/3 주기 갱신으로 흡수되지 않는 큰 조정(lease의 2/3 초과)은 이중 락 획득으로 이어질 수 있음. 분산 스케줄 실행 시각과 DB 이력 타임스탬프는 시스템 시각 정확도에 의존함 (`ASM-01`). |  하  | - **리더 교체 시 lease 재설정**: 신규 리더의 `NO_OP` apply 시 모든 락·in-flight 작업의 만료 시각을 신규 리더 시계 기준으로 다시 부여하여 노드 간 시계 차이의 영향을 제거함 (5.3.2 공통 런타임 규약 2).<br>- **단조 시계 타이머**: Heartbeat, Election Timeout, 장애 판정은 `System.nanoTime()` 기반 경과 시간으로 측정하여 시계 조정의 영향을 받지 않음.<br>- **NTP 점진 보정(slew) 운영**: `chrony` 등은 운영 중 시계를 점진 보정하고 step 조정은 기동 시에만 허용하도록 설정함 (`ASM-01`). |
| RISK-03 | 클러스터 과반수(Quorum) 노드 동시 다운 시 합의 중단 위험               | 3개 노드 중 2개 노드가 동시에 비정상 종료되거나 하드웨어 장애로 영구 손실되는 경우, 잔여 1개 노드만으로는 Quorum(2/3)을 형성하지 못해 신규 리더 선출 및 합의가 중단됨 (`ASM-06`).                                                                                           |  상  | - **홀수 노드 구성 및 K8s Anti-Affinity 적용**: 3대(또는 5대) 노드를 서로 다른 물리 호스트(Node)에 강제 분산 배치(`requiredDuringScheduling` `podAntiAffinity`)하고 `PodDisruptionBudget(minAvailable: 2)`을 적용하여 단일 하드웨어 장애 및 자발적 중단으로 인한 다중 Pod 동시 다운을 방지함.<br>- **재해 복구(DR) 수동 재구성 절차**: 과반수 영구 손실 시 가장 최신 로그(최고 term·index)를 보유한 생존 노드의 WAL을 기준으로 `RAFT_PEERS`를 재구성하여 클러스터를 재부트스트랩하는 운영 절차로 격리함. Split-Brain 위험이 있는 자동 강제 승격 API는 제공하지 않음 (`ASM-06`).                                          |
| RISK-04 | Kubernetes Pod 재생성 시 피어 IP 변경에 따른 연결 회복 지연 위험 | 크래시 후 재스케줄이나 롤링 업데이트로 Pod가 재생성되면 IP가 바뀜. ### 6.5.2 아키텍처 비위험 요인 (Non-Risks)

아키텍처 설계를 통해 위험이 구조적으로 배제된 요인은 다음과 같습니다.

| 비위험 ID | 배제된 리스크 | 판정 | 배제 근거 (설계) | 검증 연계 |
| :---: | :--- | :---: | :--- | :---: |
| NRISK-01 | Hazelcast 유료 라이선스 비용 청구 리스크 | 완전 배제 | 상용 모듈 미사용, 자체 Raft·Multi-FSM 엔진 탑재 (라이선스 비용 0원) | - |
| NRISK-02 | 외부 분산 미들웨어 장애 전파 리스크 | 완전 배제 | 외부 코디네이터 없이 In-Process 라이브러리로 구동 | `TC-QAS-08` |
| NRISK-03 | 네트워크 분할 시 Split-Brain 발생 리스크 | 완전 배제 | Raft Quorum(`(N/2)+1`) 합의, Check-Quorum 강등 | `TC-QAS-03` |
| NRISK-04 | 노드 크래시 시 미완료 작업 유실 리스크 | 완전 배제 | fsync 로컬 WAL + Raft Log 복제, `RecoveryCoordinator` 자동 복구 | `TC-QAS-06` |

1. **[NRISK-01] Hazelcast 유료 라이선스 정책 변경에 따른 TCO 증가 리스크 완전 배제**:
   - 상용 Hazelcast 모듈을 전면 배제하고 자체 경량 Raft 및 Multi-FSM 엔진을 탑재함으로써, 연간 노드당 $5,000 수준의 고정 라이선스 비용 발생 위험을 원천 제거하였습니다.
2. **[NRISK-02] 외부 미들웨어 추가 도입에 따른 단일 장애점 및 관리 부담 리스크 배제**:
   - Redis, ZooKeeper 등 별도의 외부 코디네이터 프로세스를 설치하지 않고 Spring Boot 임베디드 라이브러리로 In-Process 구동되므로, 외부 미들웨어 장애가 배치 서비스로 전파되는 리스크가 없습니다.
3. **[NRISK-03] 네트워크 파티션(Split-Brain) 시 이중 마스터 발생 리스크 배제**:
   - Raft 합의 알고리즘의 Quorum(`(N/2)+1`) 규칙이 엄격히 적용되어, 네트워크가 분할되더라도 소수파 파티션의 노드는 절대 리더로 선출되지 않으므로 이중 스케줄러 가동에 따른 데이터 왜곡 리스크가 없습니다 (검증: `TC-QAS-03`).
4. **[NRISK-04] 스케줄러 노드 크래시 시 미완료 배치 태스크 유실 리스크 배제**:
   - 태스크 실행 상태가 `fsync` 기반 로컬 WAL 및 Raft Log에 실시간 기록되며, 리더 전환 시 신규 리더의 `RecoveryCoordinator`가 추적 노드 생존 여부와 Execution Target 상태를 확인하여 재적재·추적 인수·완료를 로그로 커밋하므로 작업 누락 및 중복 실행 리스크가 없습니다 (검증: `TC-QAS-06`).
