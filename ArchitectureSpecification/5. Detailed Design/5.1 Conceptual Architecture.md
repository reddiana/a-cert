### 5.1.1 설계 전략 적용범위

Chapter 4(4.1 Architecture Design Strategy)에서 결정된 7가지 핵심 설계 의사결정(DD-01 ~ DD-07)의 채택 접근법 및 핵심 메커니즘 요약은 다음과 같습니다.

| No. | DD 명 | 채택 설계 접근법 | 핵심 설계 내용 및 대응 드라이버 |
| :--- | :--- | :--- | :--- |
| DD-01 | 클러스터 멤버십 및 리더 선출 | Socket P2P Raft 프로토콜 | TCP 소켓 기반 Raft 합의 프로토콜을 구현하여 Leader/Follower/Candidate 상태 머신과 Quorum(과반수) 합의를 통해 DB 장애 중에도 단일 리더 선출 및 멤버십 상태를 유지함 (`SF-01`, `SF-05`, `FR-04`, `QAS-03`, `QAS-04`, `QAS-05`, `NR-09`, `QAS-09`, `NR-01`, `NR-03`, `NR-04`, `NR-07`, `CR-01`, `CR-02`). |
| DD-02 | 분산 락 | Raft FSM 기반 In-Memory 분산 락 | Raft 로그로 복제되는 결정론적 인메모리 Lock FSM(FIFO 대기열, fenceToken 펜싱, lease)을 모든 노드가 동일 순서로 apply하여, DB 장애 중에도 상호 배제를 유지하고 리더 장애 시 신규 리더가 동일한 락 상태로 서비스를 이어감 (`SF-02`, `FR-01`, `NR-02`, `NR-06`, `NR-09`, `QAS-01`, `QAS-02`, `QAS-05`, `QAS-09`). |
| DD-03 | 분산 큐 | Raft FSM 기반 In-Memory 분산 큐 | 결정론적 인메모리 Queue FSM(커밋 후 인출, in-flight lease·ACK)과 로컬 WAL 영속화를 결합하여 DB I/O 없는 저지연 큐 처리를 수행함. DB 정상 시 비동기 Write-Behind로 RDBMS에 이력을 반영하고, DB 장애 중에는 인메모리 Queue FSM + 로컬 WAL로 무중단 운영을 지속함 (`SF-03`, `FR-02`, `QAS-01`, `QAS-02`, `QAS-03`, `NR-02`, `NR-09`, `QAS-09`, `CR-02`). |
| DD-04 | 장애 저널 복구 전략 | Raft 기반 분산 저널링 (Local WAL + Raft Log 복제) | 태스크 상태 변경을 fsync 기반 로컬 WAL에 기록 후 Raft Log를 통해 피어에 복제함. DB 장애 중에도 저널 기록이 유지되며, DB 복구 후 Write-Behind Reconciliation으로 RDBMS와 정합성을 복원하고 스케줄러 비정상 종료 시 무유실 자동 복구를 수행함 (`SF-04`, `FR-03`, `QAS-06`, `NR-05`, `NR-09`, `QAS-09`). |
| DD-05 | 분산 합의용 영속 저장소 | Embedded Local Disk WAL and Peer Sync | 외부 미들웨어 없이 각 노드의 로컬 디스크 WAL과 Raft Log 피어 복제로 분산 합의 상태를 영속화함. RDBMS는 최종 Write-Behind 동기화 대상으로만 활용하여 DB 장애 내구성을 확보함 (`CR-01`, `CR-02`, `NR-01`, `NR-03`, `NR-07`, `NR-09`, `QAS-08`, `QAS-09`). |
| DD-06 | 분산 코디네이터 엔진 배포 구조 | Embedded Library Pattern (임베디드 라이브러리) | 기존 BatchService JAR 내에 Raft 합의 엔진, 인메모리 Multi-FSM, 로컬 WAL 모듈을 In-Process 라이브러리로 결합 구동하여 IPC 통신 지연을 배제하고 추가 메모리 점유를 50MB 이하로 제어함 (`CR-02`, `NR-03`, `NR-05`, `NR-06`, `NR-07`, `NR-08`, `QAS-07`, `QAS-08`, `BG-03`). |
| DD-07 | K8s 복제본 관리 컨트롤러 | Kubernetes StatefulSet (StatefulSet 기반 복제본 제어) | StatefulSet 및 Headless Service를 채택하여 고정 식별자(`batch-scheduler-0`)와 DNS 엔드포인트(`batch-scheduler-0.batch-service`)를 부여함으로써 Raft P2P 통신 안정성 및 저널 소유권을 보장하고, `volumeClaimTemplates` 기반 전용 PVC 1:1 바인딩(RWO 로컬/블록 디스크)과 Quorum 보존형 기동·롤링 배포(`Parallel` 기동, 인덱스 역순 1개씩 교체, `PodDisruptionBudget`)를 지원함 (`SF-01`, `SF-05`, `CR-02`, `NR-03`, `NR-04`, `NR-08`, `NR-09`, `QAS-04`, `QAS-05`, `QAS-06`, `QAS-08`, `QAS-09`). |

### 5.1.2 개념 아키텍처 구조 (Conceptual Architecture Structure)
DD-01부터 DD-07까지의 의사결정은 개별 문제 영역에 따라 독립적으로 도출되었으나, 시스템 전반에서는 **In-Process 임베디드 라이브러리(DD-06)** 형태로 패키징되어 **단일 Raft 합의 코어(Consensus Core, DD-01/DD-05)** 를 공유하고, 그 상위에서 **도메인별 다중 상태 머신(Multi-FSM, DD-02/DD-03/DD-04)** 이 결정론적으로 구동되며, 하부의 **Kubernetes StatefulSet 및 로컬 영속 스토리지(DD-05/DD-07)** 와 결합하는 통합 아키텍처로 구성됩니다.

### 5.1.3 계층별 핵심 메커니즘 및 상호작용

#### 1. 애플리케이션 및 클라이언트 계층 (Application & Client Layer - DD-06)
- **In-Process API 호출**: 스케줄러 코어 및 워커는 분산 락(`DistributedLockExecutor`), 분산 큐(`DistributedQueueService`), 태스크 저널(`TaskJournalService`) API를 프로세스 내 표준 Java 메소드 호출 방식으로 이용합니다. 호출 노드가 팔로워이면 API가 리더로 요청을 전달하고 커밋·apply 결과만 반환합니다.
- **무간섭 캡슐화**: 상위 비즈니스 로직은 합의 및 복제 메커니즘을 직접 제어하지 않으며, API 계층을 통해 투명하게 상태 변경을 요청합니다.

#### 2. 상태 머신 계층 (Multi-FSM Layer - DD-02, DD-03, DD-04)
- **독립적 상태 도메인(Orthogonal Domains)**:
  - **Lock FSM (DD-02)**: 커밋된 `LOCK_ACQUIRE / RENEW / RELEASE / EXPIRE / CANCEL` 명령을 수신하여 락 소유자, fenceToken, lease 만료 시각(엔트리 `proposedAt` 기준) 및 FIFO 대기열을 갱신합니다.
  - **Queue FSM (DD-03)**: 커밋된 `QUEUE_ENQUEUE / DEQUEUE / RENEW / ACK / REQUEUE / REASSIGN` 명령을 수신하여 대기열과 in-flight lease 상태를 갱신합니다. 인출 대상은 `DEQUEUE` 엔트리를 apply하는 시점에 결정됩니다.
  - **Journal FSM (DD-04)**: 커밋된 `JOURNAL_RECORD` 명령을 수신하여 태스크 실행 상태(추적 노드, leaseToken)를 갱신하며, 리더의 `RecoveryCoordinator`가 이를 조회하여 고립 작업을 판정합니다.
- **결정론적 상태 전이(Deterministic State Transition)**: 모든 FSM은 Raft 합의 계층에서 확정(Commit)된 동일 순서의 로그 엔트리를 로컬 시계 없이 순차 적용(Apply)함으로써 모든 클러스터 노드 간 인메모리 상태 일관성을 보장합니다.

#### 3. 분산 합의 및 전송 계층 (Consensus Core & Transport - DD-01, DD-05)
- **단일 Raft 엔진 기반 합의 관리**: 리더 선출(`Leader`, `Follower`, `Candidate`, PreVote), 하트비트 교환, 노드 멤버십 Quorum(과반수) 판정 및 상태 변경 로그 제안을 단일 엔진(`RaftNode`)에서 전담합니다.
- **단일 포트 공유 통신 (P2P Socket Transport)**: DD-01(리더 선출/멤버십), DD-02(분산 락), DD-03(분산 큐), DD-04(저널), DD-05(WAL 피어 복제)의 모든 패킷이 단일 Raft TCP 소켓 포트(예: 7800)의 피어별 영속 연결을 공유하여 네트워크 오버헤드와 포트 개방 부담을 최소화하며, 연결 수립 시 클러스터 공유 토큰으로 노드를 인증합니다.

#### 4. 스토리지 및 인프라 오케스트레이션 계층 (Storage & Infrastructure Layer - DD-05, DD-07)
- **로컬 디스크 WAL 영속화 (DD-05)**: 모든 Raft 로그와 HardState(`currentTerm`, `votedFor`, `commitIndex`)는 각 노드의 로컬 디스크에 `fsync` 방식으로 기록되어 프로세스 강제 종료 시에도 데이터 유실을 방지합니다. 스냅샷 기반 로그 압축은 후속 구현 과제입니다 (5.4.2-4 참조).
- **Kubernetes StatefulSet 기반 제어 (DD-07)**:
  - **고정 식별자 및 DNS**: `batch-scheduler-0`과 같은 고정 서술적 식별자와 Headless Service DNS(`batch-scheduler-0.batch-service`)를 통해 Pod IP 변동과 무관하게 Raft P2P 엔드포인트를 안정적으로 유지합니다.
  - **1:1 PVC 바인딩**: `volumeClaimTemplates`를 통해 Pod별 전용 PVC(RWO 모드 로컬/블록 디스크)를 프로비저닝하여 Pod 재스케줄링 시에도 이전 WAL 로그에 재연결합니다.
  - **Quorum 보존형 기동·롤링 배포**: Readiness가 Raft Quorum 참여 상태를 기준으로 하므로 3개 Pod를 동시에 기동(`podManagementPolicy: Parallel`)하여 선출하고, 롤링 업데이트는 인덱스 역순으로 1개씩 교체하며 교체된 Pod가 Quorum에 재합류(Readiness)한 후 다음 Pod를 교체합니다. `PodDisruptionBudget(minAvailable: 2)`으로 자발적 중단 시에도 과반수를 유지하며, 리더는 인덱스로 고정되지 않으므로 리더 Pod 교체 시 3초 이내 재선출로 합의 연속성을 유지합니다.

#### 5. 비동기 데이터베이스 정합 계층 (Write-Behind Synchronization Layer)
- **Write-Behind 비동기 파이프라인**: 리더의 `WriteBehindSynchronizer`가 커밋 인덱스를 주기적으로 확인하여, 별도 메모리 버퍼 없이 로컬 WAL의 커밋 구간을 판독해 RDBMS에 일괄 반영합니다. 이력 반영과 동기화 체크포인트 갱신은 단일 트랜잭션으로 커밋됩니다.
- **DB 장애 격리(Fault Isolation)**: 메타 RDBMS 연결이 차단되더라도 합의(Consensus) 및 FSM 상태 변경은 인메모리와 로컬 WAL을 통해 정상 처리되며, 주 트랜잭션 경로가 차단되지 않습니다.

### 5.1.4 런타임 제어 흐름 및 장애 격리 메커니즘

#### 1. 정상 상태의 분산 상태 전이 라이프사이클 (State Transition Flow)
1. **클라이언트 요청 접수**: DAG 스케줄러 엔진이 In-Process API(Lock/Queue/Journal)를 호출합니다. 호출 노드가 팔로워이면 요청이 리더로 전달됩니다.
2. **Raft Log 생성 및 로컬 기록**: 리더 노드는 수신된 명령을 Raft Log 엔트리로 패키징하여 로컬 WAL에 기록하고, 다건 엔트리를 1회 `fsync`로 영속화(Group Commit)합니다.
3. **P2P Quorum 복제**: 리더 노드는 `AppendEntries` RPC를 통해 팔로워 노드들에 로그를 병렬 복제하며, 팔로워는 로그 일관성(`prevLogIndex`/`prevLogTerm`) 확인과 `fsync` 후 응답합니다.
4. **Quorum Commit 확정**: 클러스터 과반수(Quorum, 예: 3노드 중 2노드) 노드에서 영속화 응답이 수신되고 해당 엔트리가 현재 term이면 `Committed`로 판정합니다.
5. **Multi-FSM 동시 적용(Apply)**: 커밋된 로그 엔트리는 각 도메인 FSM(Lock/Queue/Journal)으로 전달되어 인메모리 상태를 갱신하고, 리더 노드는 클라이언트에 apply 결과를 반환합니다.
6. **Write-Behind 비동기 반영**: 리더의 `WriteBehindSynchronizer`가 DB 체크포인트 이후의 커밋 구간을 WAL에서 판독하여 백그라운드에서 RDBMS에 배치 반영합니다.

#### 2. 메타 DB 장애 격리 및 지속 운영 메커니즘 (DB Failure Tolerance)
- **장애 감지 및 버퍼링**: RDBMS 연결 실패 시 Write-Behind Worker는 재시도 백오프 모드(1s → 10s 상한)로 전환되며, 미반영 이력은 로컬 WAL에 안전하게 보존됩니다 (DB 체크포인트 이전 구간만 압축 대상).
- **무중단 운영 지속**: 리더 선출(DD-01), 분산 락(DD-02), 분산 큐(DD-03), 저널링(DD-04)의 모든 상태 판정 및 변경이 Raft P2P 채널과 로컬 WAL만으로 완결되므로, DB 다운 상태에서도 분산 오케스트레이션이 지속됩니다.

#### 3. 노드 장애 및 리더 Failover 메커니즘 (Node/Leader Failover)
- **일반 팔로워 장애**: 리더가 팔로워별 `AppendEntries` 응답 수신 시각을 추적하여 2초 무응답 시 장애로 판정하고, 멤버십 변경(`MEMBER_STATUS`)을 과반수 커밋하여 3초 이내에 전 노드의 활성 멤버십을 갱신합니다. Quorum 산정 분모는 유지되며, 남은 과반수 노드가 유지되는 한 클러스터 기능은 중단 없이 유지됩니다.
- **리더 노드 장애**: Election Timeout(1.5~2.0초 난수) 경과 시 후보자 노드가 PreVote·RequestVote(로그 최신성 검사)로 3초 이내에 신규 리더를 선출합니다. 신규 리더는 현재 term의 `NO_OP` 엔트리를 커밋하여 이전 로그를 확정한 뒤 서비스를 개시하며, 모든 노드는 복제된 로그를 이미 apply하고 있으므로 Multi-FSM 상태가 즉시 이어집니다.

#### 4. DB 복구 시 정합성 복원 메커니즘 (Reconciliation Lifecycle)
- **복구 감지 및 순차 정합**: 메타 RDBMS 커넥션이 복구되면, 리더의 `WriteBehindSynchronizer`가 DB 동기화 체크포인트(`batch_sync_checkpoint`)를 조회하여 그 이후의 미동기화 구간을 로그 인덱스 순서대로 RDBMS에 재생(Replay)합니다. 동일 구간의 재반영은 로그 인덱스 기준으로 멱등 처리되어 리더 교체 중에도 중복 없이 최종 정합성을 복원합니다.
