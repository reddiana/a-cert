#### 1. 배포 아키텍처 토폴로지 (Deployment Topology)

Kubernetes 클러스터는 비즈니스 배치 작업의 고부하가 스케줄링 및 분산 합의 코어 엔진에 영향을 주는 간섭(Noisy Neighbor) 현상을 배제하기 위해, **스케줄러 전용 네임스페이스(`ns-batchservice`)** 와 **배치 실행 전용 네임스페이스(`ns-batch`)** 를 **물리적으로 완전히 분리된 전용 VM 노드 풀(Dedicated NodePool)** 에 격리 배치합니다.

- **`ns-batchservice` 네임스페이스 (Core Orchestration Tier - 전용 스케줄러 VM 풀)**:
  - **전용 인프라 (`nodepool: batch-service`)**: 스케줄링 및 Raft 합의 전용으로 분리된 3대의 독립 VM에 배포됩니다.
  - StatefulSet 컨트롤러에 의해 3개의 복제본 Pod(`batch-scheduler-0, 1, 2`)가 구동됩니다. **리더는 Pod 인덱스로 고정되지 않으며** Raft 선출(PreVote/RequestVote)로 결정됩니다.
  - 각 Pod는 단일 컨테이너(JVM OpenJDK 17) 내에 스케줄러 애플리케이션과 In-Process 라이브러리(`DD-06`)인 `batch-clustering-engine`을 단일 프로세스로 통합 실행합니다. 엔진은 Spring Boot 자동 구성(`BatchClusteringAutoConfiguration`)으로 합의 엔진(`RaftNode`), 전송 계층(`SocketNetworkTransport`), Multi-FSM(`ClusterStateMachine`), 로컬 WAL 관리자(`RaftLogManager`), DB 동기화(`WriteBehindSynchronizer`), 고립 작업 복구(`RecoveryCoordinator`)를 기동합니다.
  - 노드 간 분산 합의(Raft P2P)는 Headless Service(`batch-service`)의 DNS 디스커버리와 단일 Raft TCP 포트(`7800/TCP`)를 통해 직접 수행(`DD-01`, `DD-07`)되며, 연결 수립 시 클러스터 공유 토큰(`RAFT_AUTH_TOKEN`)으로 상호 인증합니다.
  - 각 Pod의 WAL은 Pod별 전용 PVC(`ReadWriteOnce`, 10GiB)를 `/var/data/batch/wal`에 마운트하여 `{wal-dir}/{nodeId}/` 하위에 영속화(`DD-05`, `DD-07`)합니다.
  - `WriteBehindSynchronizer`는 **리더 Pod에서만 활성화**되어 중앙 `Meta RDBMS`와 Spring DataSource(HikariCP) JDBC 커넥션 풀로 비동기 상태 정합을 수행합니다.
- **`ns-batch` 네임스페이스 (Execution Environment Tier - 전용 배치 실행 VM 풀)**:
  - **전용 인프라 (`nodepool: batch-execution`)**: 비즈니스 배치 프로세스 실행 전용으로 분리된 다중 VM 노드 풀에 배포됩니다.
  - 스케줄러 노드의 `BatchLauncher`에 의해 디스패치된 대용량 비즈니스 배치 작업(Target Pods / Jobs)이 물리적으로 격리된 컴퓨팅 자원에서 독립적으로 구동되므로, CPU/메모리 스파이크 및 디스크 I/O 경합이 스케줄러 엔진에 전이되지 않습니다.
  - 리더의 `RecoveryCoordinator`는 수요처가 구현한 `ExecutionStatusProvider`를 통해 `ns-batch`의 Job/Pod 실행 상태를 조회하여 고립 작업을 판정합니다 (5.3.2 Scenario 2).

### 5.4.2 Production Deployment Specification

본 절은 Kubernetes 환경에서 분산 배치 스케줄러 시스템을 운영 배포하기 위한 구체적인 인프라 구성 규격과 파라미터를 정의합니다. 각 세부 영역별 설계 의도와 함께 해당하는 Kubernetes 매니페스트 및 애플리케이션 설정을 항목별로 분리하여 기술합니다.

#### 1. 워크로드 컨트롤러 및 복제본 관리 정책 (Workload Controller & Replica Policy - DD-07)

* **StatefulSet 컨트롤러 채택 사유 (`DD-07`, `CR-02`, `NR-08`)**:
  * `ns-batchservice` 네임스페이스 내에서 Pod별로 고정된 서술적 인덱스(`batch-scheduler-0`, `batch-scheduler-1`, `batch-scheduler-2`)를 보장합니다.
  * Pod가 재기동되거나 다른 호스트 노드로 재스케줄링되더라도 동일한 식별자(= Raft `nodeId`)와 PVC를 승계하여, 기존 WAL로 상태를 복원한 뒤 클러스터에 재합류합니다(5.3.2 Scenario 3, `QAS-06`).
* **복제본 수(Replicas) 및 Quorum 정합성 (`SF-01`, `QAS-03`, `QAS-05`)**:
  * 복제본 수(`replicas`)는 3개로 구성하여 과반수(Quorum = 2) 합의 체계를 형성합니다. Quorum 분모는 `RAFT_PEERS`에 명시된 전체 노드 수로 고정되며, 장애 노드가 멤버십에서 제외되어도 축소되지 않습니다.
  * 단일 노드 장애 시에도 합의가 지속되며, 네트워크 분할 시 소수파는 커밋·인출이 불가능하여 Split-Brain을 방지(`QAS-03`)합니다.
  * 복제본 수 변경(스케일 아웃/인)은 `RAFT_PEERS` 변경과 전체 재배포를 수반합니다 (동적 멤버십 변경 미지원).
* **Pod 관리 정책 (`podManagementPolicy: Parallel`)**:
  * Readiness Probe가 Raft Quorum 참여 상태(리더 확인)를 기준으로 판정하므로, `OrderedReady`를 사용하면 `batch-scheduler-0` 단독으로는 과반수 선출이 불가능하여 Ready에 도달하지 못하고 후속 Pod가 생성되지 않는 **기동 교착**이 발생합니다.
  * 따라서 3개 Pod를 동시에 생성하는 `Parallel` 정책을 적용하며, 선출은 Raft 프로토콜이 담당합니다.
* **순차적 롤링 업데이트 정책 (`NR-04`, `QAS-04`, `QAS-05`)**:
  * `updateStrategy.type: RollingUpdate`: `podManagementPolicy`와 무관하게 인덱스 역순(`batch-scheduler-2` → `1` → `0`)으로 1개씩 교체하며, 교체된 Pod가 Ready(Quorum 재합류)가 된 후 다음 Pod를 교체하므로 동시에 2개 이상이 이탈하지 않습니다.
  * 리더는 인덱스로 고정되지 않으므로, 교체 대상 Pod가 리더인 경우 해당 Pod 종료 시 잔여 노드에서 3초 이내 신규 리더가 선출됩니다(`QAS-05`). 롤링 업데이트 1회당 리더 교체는 최대 1~2회 발생할 수 있습니다.
  * 종료 시 엔진은 스레드 정지 후 `commitIndex`를 영속화(graceful stop)하며, 미커밋 요청은 클라이언트가 동일 `requestId`로 신규 리더에 재시도합니다.
* **자발적 중단 보호 (`PodDisruptionBudget`)**: 노드 드레인 등 자발적 중단 시에도 Quorum(2개) 이상이 유지되도록 `minAvailable: 2`를 적용합니다.

##### [매니페스트 설정: 워크로드 컨트롤러 및 복제본 정책]
```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: batch-scheduler
  namespace: ns-batchservice
  labels:
    app: batch-scheduler
spec:
  serviceName: batch-service
  replicas: 3
  podManagementPolicy: Parallel
  updateStrategy:
    type: RollingUpdate
  selector:
    matchLabels:
      app: batch-scheduler
  template:
    metadata:
      labels:
        app: batch-scheduler
    spec:
      serviceAccountName: batch-scheduler
      terminationGracePeriodSeconds: 30
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: batch-scheduler-pdb
  namespace: ns-batchservice
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: batch-scheduler
```

#### 2. 네트워크 토폴로지 및 서비스 디스커버리 (Network Topology & Service Discovery - DD-01, DD-06)

##### 1) Kubernetes Headless Service 구성 (`CR-02`, `NR-09`)
* `ns-batchservice` 네임스페이스 내에 `clusterIP: None`으로 설정된 Headless Service(`batch-service`)를 생성합니다.
* StatefulSet의 각 Pod는 고정된 FQDN을 통해 상호 탐색됩니다.
  * FQDN 포맷: `batch-scheduler-{index}.batch-service.ns-batchservice.svc.cluster.local`
* **`publishNotReadyAddresses: true`**: Readiness는 Raft 리더가 확인된 이후에만 `true`가 되므로, 기동 직후 아직 Ready가 아닌 Pod들도 서로의 DNS 레코드를 조회할 수 있어야 선출이 가능합니다. 이 설정이 없으면 Pod 간 P2P 연결이 수립되지 않아 기동 교착이 발생합니다.
* 외부(수요처 API) 트래픽을 위한 일반 Service는 Readiness를 따르는 별도 Service로 분리합니다.

##### [매니페스트 설정: Headless Service]
```yaml
apiVersion: v1
kind: Service
metadata:
  name: batch-service
  namespace: ns-batchservice
  labels:
    app: batch-scheduler
spec:
  clusterIP: None
  publishNotReadyAddresses: true
  selector:
    app: batch-scheduler
  ports:
    - name: raft-p2p
      port: 7800
      targetPort: 7800
      protocol: TCP
    - name: http-api
      port: 8080
      targetPort: 8080
      protocol: TCP
```

##### 2) 컨테이너 포트 규격 (`4.2.1절 SW Stack` 준수)
* **Raft P2P 통신 포트 (`7800/TCP`)**:
  * DD-01(Leader Election), DD-02(Lock), DD-03(Queue), DD-04(Journal), DD-05(WAL Peer Sync)와 클라이언트 요청 전달(`ClientRequest`)을 포함한 모든 분산 합의 트래픽이 공유하는 단일 전용 포트입니다.
  * 피어별 영속 TCP 연결 1개로 순서를 보장하며, 연결 수립 시 공유 토큰 핸드셰이크로 인증합니다. 메시지는 길이 프리픽스 바이너리 프레임으로 교환하며 Java 기본 직렬화를 사용하지 않습니다.
* **애플리케이션 API 및 메트릭 포트 (`8080/TCP`)**:
  * REST API 요청 처리, Spring Boot Actuator 상태 점검(Probe) 및 메트릭 수집용 포트입니다.

##### [매니페스트 설정: 컨테이너 포트 (ports)]
```yaml
containers:
  - name: batch-scheduler
    image: internal-registry.company.com/batch/batch-service:1.0.0
    imagePullPolicy: IfNotPresent
    ports:
      - containerPort: 7800
        name: raft-p2p
        protocol: TCP
      - containerPort: 8080
        name: http-api
        protocol: TCP
```

##### 3) 클러스터 디스커버리 및 런타임 환경변수 (`DD-01`, `DD-06`)
* `RAFT_NODE_ID`에 `POD_NAME`을 매핑하여 노드 식별성을 승계합니다 (`RAFT_NODE_ID` 미설정 시 엔진이 `POD_NAME`을 사용).
* `RAFT_PEERS`에 Headless Service FQDN 기반 3개 노드 엔드포인트(`host:port`, 자기 자신 포함 가능)를 콤마로 명시합니다. 엔진은 호스트의 첫 DNS 레이블(`batch-scheduler-0`)을 각 노드의 `nodeId`로 사용하고 자기 자신은 피어에서 제외합니다.
* `RAFT_AUTH_TOKEN`은 Kubernetes Secret에서 주입하며, **다중 노드 구성에서 필수**입니다(미설정 시 기동 실패).
* `RAFT_PEERS`가 비어 있으면 Split-Brain 방지를 위해 기동이 실패합니다(개발 환경 전용 `batch.cluster.allow-single-node=true` 제외).
* JDBC DataSource URL과 WAL 저장 경로를 주입합니다. DataSource가 없으면 Write-Behind만 비활성화되고 합의·락·큐는 정상 동작합니다.

#### 3. 영속 스토리지 및 볼륨 마운트 정책 (Persistent Storage & Volume Policy - DD-05, DD-07)

##### 1) `volumeClaimTemplates` 기반 전용 PVC 바인딩 (`DD-05`, `DD-07`, `QAS-08`)
* StatefulSet 매니페스트 내 `volumeClaimTemplates`를 정의하여 Pod별로 독립적인 PVC(예: `wal-storage-batch-scheduler-0`)를 1:1로 자동 프로비저닝합니다.
* `accessModes: [ "ReadWriteOnce" ] (RWO)`: 단일 노드 전용 쓰기 모드를 적용하여 스토리지 동시 쓰기 충돌을 방지하며, 외부 분산 파일 시스템(NFS, EFS 등)에 종속되지 않고 `fsync` 지연이 낮은 로컬 디스크 또는 블록 스토리지(SSD 계열 StorageClass)를 사용합니다 (`CR-02`, `NR-03`).
* 용량: 노드당 10GiB (후술하는 상세 사이징 산정 근거 참조)

##### [매니페스트 설정: StatefulSet volumeClaimTemplates]
```yaml
volumeClaimTemplates:
  - metadata:
      name: wal-storage
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 10Gi
```

##### 2) 컨테이너 볼륨 마운트 및 데이터 무유실 연속성 (`QAS-06`, `QAS-09`)
* 마운트 경로: `/var/data/batch/wal` (`WAL_DATA_DIR`), 노드별 실제 파일: `/var/data/batch/wal/{nodeId}/raft.log`, `hardstate`
* Pod 장애로 인한 재시작 시, Kubernetes가 기존 PVC를 동일 식별자의 새 Pod에 재마운트하며 엔진은 다음 순서로 복원합니다.
  1. `hardstate`에서 `currentTerm`, `votedFor`, 영속화된 `commitIndex`를 로드
  2. `raft.log` 프레임을 순차 판독하며 CRC를 검증하고, 부분 기록·손상된 꼬리 프레임은 절단
  3. 영속화된 `commitIndex`까지 Multi-FSM에 Replay하여 락·큐·저널·멤버십 상태 복원
  4. Follower로 기동하여 리더로부터 누락 구간을 따라잡은 뒤 `MEMBER_STATUS(ALIVE)` 커밋 시 Readiness 복귀 (5.3.2 Scenario 3)

##### [매니페스트 설정: 컨테이너 volumeMounts]
```yaml
containers:
  - name: batch-scheduler
    volumeMounts:
      - name: wal-storage
        mountPath: /var/data/batch/wal
```

#### 4. 인프라 자원, 물리적 VM 격리 및 프로브 정책 (Capacity Sizing & Resource / Node Isolation - DD-06, QAS-07)

시스템의 안정적 운영을 위한 컨테이너 컴퓨팅 자원(CPU, 메모리) 및 영속 스토리지(PVC)의 정량적 용량 산정(Sizing) 근거와 물리적 VM 격리, 프로브 정책은 다음과 같습니다.

##### 1) 워크로드 특성 및 산정 기준 데이터
- **일일 최대 배치 태스크 수**: 약 10,000건
- **태스크당 로그 엔트리 수**: 태스크 1건당 약 6~8건 (`LOCK_ACQUIRE`, `QUEUE_ENQUEUE`, `QUEUE_DEQUEUE`, `JOURNAL_RECORD(RUNNING)`, `JOURNAL_RECORD(COMPLETED)`, `QUEUE_ACK`, `LOCK_RELEASE` 등)
- **일일 총 로그 엔트리 수**: $10,000 \times 8 = 80,000\text{건/일}$ (Heartbeat는 로그 엔트리를 생성하지 않음)
- **피크 타임 부하**: 자정 및 영업 마감 시 동시 100건 DAG 상태 전이(`QAS-01`), 동시 200건 큐 인출 경합(`QAS-02`)

##### 2) 컨테이너 CPU 및 메모리 자원 사이징 (`DD-06`, `QAS-07`, `NR-06`)

* **CPU 자원 사이징 (Requests: 500m / Limits: 2000m)**:
  * **Requests (500m)**: 평시 Heartbeat(500ms 주기) 송수신, 20ms 주기 타이머 틱, 1초 주기 복구 스캔 등 유휴 부하(0.1~0.2 Core)를 안정적으로 수용. In-Process 라이브러리 구조(`DD-06`)로 사이드카 IPC 오버헤드가 없음.
  * **Limits (2000m)**: 피크 타임 동시 100건 DAG 전이(`QAS-01`), 200건 큐 인출(`QAS-02`)의 Group Commit·복제 처리, 리더 장애 시 선출 및 복구(`QAS-05`, `QAS-06`), DB 복구 시 Write-Behind 대량 동기화(`QAS-09`)에서 발생하는 일시적 CPU 버스팅을 수용하여 Throttling 방지.

* **메모리(JVM Heap / Off-Heap) 사이징 (Requests: 1Gi / Limits: 2Gi)**:
  * **JVM Heap (Xms: 512MB / Xmx: 1024MB)**:
    * 기본 Spring Boot 풋프린트: 약 250MB ~ 300MB
    * In-Memory Multi-FSM 상태: Lock FSM(1MB) + Queue FSM(20MB) + Journal FSM(20MB) = **약 41MB** (`QAS-07`의 추가 Heap 50MB 이하 요건 충족)
    * requestId 멱등 결과 캐시: 최근 50,000건 상한 (수 MB 이내)
    * GC 워킹 메모리 및 임시 객체 버퍼: 피크 시 약 400MB~500MB (G1GC 적용 시 STW 1초 이내 유지)
  * **Off-Heap & Native**: Metaspace, Thread Stack, 소켓 버퍼 및 WAL FileChannel 버퍼 약 **500MB**
  * **K8s Container Quota**: 평시 800MB 사용량을 고려해 **Requests 1Gi** 설정, OOMKilled 방지를 위해 100% 안전 마진을 둔 **Limits 2Gi** 설정.

> [!WARNING] 현재 구현 제약: 로그 압축(Snapshot/Compaction) 미구현
> `RaftLogManager`는 WAL 파일과 함께 **전체 로그 엔트리를 메모리에 유지**하며, 기동 시 전체 WAL을 Replay합니다. Snapshot/InstallSnapshot/로그 압축은 아직 구현되지 않았으므로(압축 하한선 관리만 구현), 운영 부하(80,000건/일) 기준으로 Heap이 일 약 40~70MB씩 증가하고 재기동 Replay 시간도 누적 증가합니다. 장기 무중단 운영 전 로그 압축 구현이 **필수 선행 과제**이며, 도입 전까지는 Heap 사용량·WAL 크기 모니터링과 계획된 클러스터 초기화 절차로 관리합니다 (6.5 위험 요인, 7.1.5 검증 한계 연계).

##### [매니페스트 설정: 컨테이너 자원 할당 (resources)]
```yaml
containers:
  - name: batch-scheduler
    resources:
      requests:
        cpu: "500m"
        memory: "1Gi"
      limits:
        cpu: "2000m"
        memory: "2Gi"
```

##### 3) 영속 스토리지(PVC) 용량 사이징 (10GiB / ReadWriteOnce)

| 항목 | 계산 요소 및 파라미터 | 산출 용량 |
| :--- | :--- | :--- |
| **1) 단일 WAL 엔트리 크기** | 프레임 헤더(length·CRC 8B) + index·term·proposedAt(24B) + 명령 유형·requestId(약 40B) + 명령 속성(jobId, owner, token 등 약 100~300B), 보수적 상한 적용 | **약 512 Bytes / 엔트리** |
| **2) 일일 순수 WAL 생성량** | $80,000\text{ 엔트리/일} \times 512\text{ Bytes}$ | **약 40 MB / 일** |
| **3) DB 장기 장애 대비 보존 용량** | 메타 DB 장기 장애(`QAS-09`) 시 최대 7일간 DB 미반영 구간 보존 ($40\text{ MB/일} \times 7\text{일}$). 압축은 DB 체크포인트 이전 구간에만 허용 | **약 280 MB** |
| **4) Raft FSM 스냅샷 보관 용량** *(압축 구현 시)* | FSM 상태 덤프 스냅샷(50MB) $\times$ 최근 3세대 롤링 보관 | **약 150 MB** |
| **5) 로그 압축(Compaction) 버퍼** *(압축 구현 시)* | 세그먼트 롤링 및 압축 처리 중 임시 파일 버퍼 (2배수) | **약 600 MB** |
| **6) 파일시스템 오버헤드 및 안전율** | 파일시스템 메타데이터 공간 및 피크 트래픽(10배 폭증) 수용 안전 마진 | **약 1,000 MB** |
| **총 산출 최소 요구 용량** | $(3) + (4) + (5) + (6)$ | **약 2.03 GiB** |
| **최종 프로비저닝 용량** | **K8s StorageClass 최소 할당 단위 및 장기 무점검 안전 운영 기준 적용** | **10 GiB** (ReadWriteOnce) |

* **사이징 요약 결론**:
  * 로그 압축 구현 후에는 메타 DB가 1주일 이상 장기 중단(`QAS-09`)되거나 일일 작업량이 5배 폭증하더라도 디스크 사용률이 30% 이하로 제어됩니다.
  * **압축 미구현 상태(현재)** 에서는 WAL이 일 약 40MB씩 누적되어 10GiB 기준 약 250일 후 포화되므로, PVC 사용률 70% 경보를 설정하고 압축 구현 전까지 계획된 초기화 절차로 관리합니다.

##### 4) 물리적 VM 노드 풀 분리 및 고가용성 격리 정책 (`QAS-03`, `QAS-04`, `QAS-05`)

* **물리적 VM 노드 풀 분리 (Dedicated NodePool Isolation)**:
  * **목적**: `ns-batch`에서 실행되는 비즈니스 배치 작업(대용량 데이터 집계, I/O 부하 등)이 `ns-batchservice`의 스케줄링 및 Raft 합의 엔진에 미치는 CPU Spike, Memory Pressure, Network I/O 경합, `fsync` 지연 등의 간섭(Noisy Neighbor 문제)을 물리적으로 차단합니다.
  * **격리 구현 메커니즘**:
    * **Node Taints & Tolerations**: 스케줄러 전용 VM 노드에 `workload=batch-service:NoSchedule` Taint를 설정하고, `batch-scheduler` Pod에만 해당 Toleration을 부여하여 일반/배치 실행 워크로드의 스케줄러 VM 진입을 차단합니다.
    * **NodeSelector / NodeAffinity**:
      * `batch-scheduler` Pod: `nodeSelector: nodepool: batch-service`를 통해 스케줄러 전용 VM에만 배포.
      * `ns-batch`의 실행 타겟 Pod/Job: `nodeSelector: nodepool: batch-execution`을 통해 배치 실행 전용 VM에만 배포.
* **스케줄러 노드 간 상호 분산 (Pod Anti-Affinity - `QAS-03`, `QAS-04`, `QAS-05`)**:
  * 3개의 스케줄러 Pod가 단일 VM에 중복 배치되면 해당 VM 장애 시 Quorum이 붕괴되므로, `requiredDuringSchedulingIgnoredDuringExecution` 기반 `podAntiAffinity`(`topologyKey: "kubernetes.io/hostname"`)를 적용하여 3대의 서로 다른 VM에 1개씩 **강제** 분산 배치합니다.
  * 이를 통해 단일 VM 하드웨어 고장 시에도 2개 노드가 생존하여 Raft Quorum(과반수 합의)을 유지합니다. 전용 VM이 3대 미만이면 Pod가 Pending 상태로 남으므로 노드 풀 최소 3대를 보장합니다.

##### [매니페스트 설정: 물리적 VM 격리 및 고가용성 분산 (nodeSelector, tolerations, affinity)]
```yaml
spec:
  template:
    spec:
      # [물리적 VM 격리] 스케줄러 전용 노드 풀 지정
      nodeSelector:
        nodepool: batch-service
      # [물리적 VM 격리] 전용 노드 Taint 허용
      tolerations:
        - key: "workload"
          operator: "Equal"
          value: "batch-service"
          effect: "NoSchedule"
      affinity:
        # [고가용성 분산] 서로 다른 호스트 VM에 1개씩 강제 분산 (Quorum 보호)
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - batch-scheduler
              topologyKey: "kubernetes.io/hostname"
```

##### 5) 컨테이너 라이프사이클 프로브 정책 (Probes - `QAS-04`, `QAS-05`)
* **Startup Probe**: 엔진은 Spring 컨텍스트 기동 과정에서 WAL Replay와 Multi-FSM 복원을 완료하므로, 애플리케이션 기동 완료(`/actuator/health/liveness` 응답)로 복원 완료를 판정합니다 (failureThreshold: 30, periodSeconds: 2 → 최대 60초). 로그 압축 미구현 상태에서는 WAL 누적에 따라 Replay 시간이 증가하므로 기동 시간 추이를 모니터링합니다.
* **Liveness Probe**: 프로세스 Deadlock 등 JVM 비정상 상태만 감지합니다(`livenessState`). **Raft 상태는 포함하지 않아**, 네트워크 분할로 소수파에 고립된 노드가 재기동 루프에 빠지지 않도록 합니다 (periodSeconds: 5).
* **Readiness Probe**: `readiness` 그룹(`readinessState`, `raft`)으로 Raft Quorum 참여 상태를 확인합니다. `RaftHealthIndicator`는 리더가 확인되고, 리더면 현재 term `NO_OP` 커밋 완료, 팔로워면 커밋된 멤버십상 ALIVE일 때 `UP`을 반환합니다. **DB Health는 포함하지 않아** 메타 DB 장애가 스케줄러 Pod 트래픽 차단으로 전파되지 않습니다 (periodSeconds: 3).

##### [매니페스트 설정: 라이프사이클 프로브 (startupProbe, livenessProbe, readinessProbe)]
```yaml
containers:
  - name: batch-scheduler
    startupProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080
      initialDelaySeconds: 3
      periodSeconds: 2
      failureThreshold: 30
    livenessProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 3
    readinessProbe:
      httpGet:
        path: /actuator/health/readiness
        port: 8080
      periodSeconds: 3
      timeoutSeconds: 2
      failureThreshold: 2
```

##### 6) 물리적 VM 노드(인프라) 사이징 규격 (Host VM Capacity Sizing - `QAS-07`, `QAS-08`, `CR-02`)

컨테이너 자원 할당량 외에 Kubernetes 플랫폼 구동(Kubelet, Container Runtime, CNI/CSI 플러그인) 및 Host OS 기본 구동에 필요한 예약 자원(`kube-reserved`, `system-reserved`)을 고려한 물리적/가상 VM 인프라의 권장 사이징 규격은 다음과 같습니다.

###### 가. 노드 풀별 VM 인프라 사이징 매트릭스

| 노드 풀 명칭 | 인스턴스 수 | 권장 VM 규격 (노드당) | 스토리지 규격 (노드당) | 사이징 산정 근거 및 역할 |
| :--- | :---: | :--- | :--- | :--- |
| **`nodepool: batch-service`<br>(스케줄러 전용 노드 풀)** | **3대**<br>(독립 VM, 최소 3대 필수) | • **vCPU**: 2 Core (권장: 4 Core)<br>• **Memory**: 4 GiB (권장: 8 GiB)<br>• **네트워크**: 1 Gbps 이상 | • **OS Root Disk**: 50 GiB (SSD/NVMe)<br>• **WAL 영속 볼륨**: 10 GiB PVC (RWO, SSD 계열) | • `batch-scheduler` Pod Limits(2 Core / 2 GiB) 수용<br>• Node 시스템 예약분(1 Core / 1~2 GiB) 확보<br>• 필수 `podAntiAffinity`로 1 VM당 1 Pod 배치 (`QAS-03`, `QAS-05`) |
| **`nodepool: batch-execution`<br>(배치 실행 전용 노드 풀)** | **가변**<br>(N대) | • **vCPU**: 4~16 Core<br>• **Memory**: 8~32 GiB<br>• **네트워크**: 1~10 Gbps | • **OS Root Disk**: 100 GiB 이상 (SSD)<br>• **임시 스토리지**: 워크로드별 산정 | • 수요처 프로젝트의 비즈니스 배치 작업 부하에 종속 (`CR-02`)<br>• 동시 실행 배치 Pod 수 및 작업별 메모리/CPU 사용량에 비례<br>• Cluster Autoscaler 연동을 통한 동적 확장 권장 |

###### 나. 스케줄러 전용 VM 풀(`batch-service`) 세부 자원 산출 내역

1. **CPU 산출**:
   - 스케줄러 컨테이너 Limits: `2,000m (2 Core)`
   - Host OS 및 K8s 시스템 컴포넌트(Kubelet, CNI, 로그 수집기 등) 예약: `500m ~ 1,000m (0.5 ~ 1 Core)`
   - **최소 요구량**: 2.5 ~ 3 Core $\rightarrow$ **표준 4 vCPU VM 인스턴스 권장** (최소 2 vCPU 환경에서도 안정 수용 가능, `QAS-07`)
2. **메모리 산출**:
   - 스케줄러 컨테이너 Limits: `2 GiB` (JVM Heap 1GiB + Native/Off-Heap 1GiB)
   - Host OS 및 K8s 시스템 컴포넌트 예약: `1.5 ~ 2 GiB`
   - **최소 요구량**: 3.5 ~ 4 GiB $\rightarrow$ **표준 4 GiB ~ 8 GiB RAM VM 인스턴스 권장**
3. **스토리지 산출**:
   - OS 및 K8s 이미지 레이어/바이너리: `30 ~ 40 GiB`
   - 스케줄러 전용 로컬 WAL 영속 볼륨: `10 GiB` (StatefulSet `volumeClaimTemplates`를 통한 RWO 블록 디스크 연결). WAL은 Group Commit `fsync` 지연이 합의 지연에 직결되므로 SSD 계열 StorageClass를 사용합니다.
   - **최소 요구량**: 노드당 Root Disk 50 GiB + WAL 전용 스토리지 10 GiB

#### 5. 보안 및 운영 연계 정책 (Security & Operational Integration - DD-01, DD-04, DD-05)

##### 1) Raft P2P 포트 접근 제어 (`NetworkPolicy`)
* 엔진은 연결 수립 시 공유 토큰으로 노드를 인증하지만 전송 구간 암호화(mTLS)는 제공하지 않으므로, `7800/TCP`는 **동일 StatefulSet Pod 간에만** 허용하도록 NetworkPolicy로 제한합니다.
* 전송 구간 암호화가 요구되는 환경에서는 서비스 메시(mTLS)를 함께 적용합니다.
* `RAFT_AUTH_TOKEN` Secret은 배포 파이프라인에서 생성하여 주입하고, 교체 시 3개 Pod를 함께 재배포합니다(토큰이 다른 노드 간 연결은 거부됨).

##### [매니페스트 설정: NetworkPolicy]
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: batch-scheduler-raft
  namespace: ns-batchservice
spec:
  podSelector:
    matchLabels:
      app: batch-scheduler
  policyTypes:
    - Ingress
  ingress:
    # Raft P2P: 동일 StatefulSet Pod 간에만 허용
    - from:
        - podSelector:
            matchLabels:
              app: batch-scheduler
      ports:
        - port: 7800
          protocol: TCP
    # HTTP API / Actuator
    - ports:
        - port: 8080
          protocol: TCP
```

##### 2) Execution Target 상태 조회 권한 (`RBAC`, DD-04)
* 리더의 `RecoveryCoordinator`는 수요처가 구현한 `ExecutionStatusProvider` 빈을 통해 `ns-batch`의 Job/Pod 상태를 조회하여 고립 작업의 인수·재적재·완료를 판정합니다(5.3.2 Scenario 2).
* 이를 위해 스케줄러 ServiceAccount에 `ns-batch`의 Job/Pod **읽기 권한만** 부여합니다.
* `ExecutionStatusProvider` 빈을 등록하지 않으면 기본 구현이 `UNKNOWN`을 반환하여 고립 작업을 재적재(At-least-once)하므로, 재실행이 불가능한 작업을 운영하는 수요처는 반드시 구현합니다.

##### [매니페스트 설정: ServiceAccount 및 RBAC]
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: batch-scheduler
  namespace: ns-batchservice
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: batch-execution-status-reader
  namespace: ns-batch
rules:
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["get", "list"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: batch-scheduler-execution-status-reader
  namespace: ns-batch
subjects:
  - kind: ServiceAccount
    name: batch-scheduler
    namespace: ns-batchservice
roleRef:
  kind: Role
  name: batch-execution-status-reader
  apiGroup: rbac.authorization.k8s.io
```

##### 3) 메타 DB 동기화 스키마 (DD-05, QAS-09)
* `WriteBehindSynchronizer`는 이력 반영(`batch_journal_log`)과 체크포인트 갱신(`batch_sync_checkpoint`)을 단일 트랜잭션으로 커밋하며, 동일 `log_index` 구간 재반영 시 삭제 후 삽입으로 멱등 처리합니다.
* 운영 DB에는 아래 DDL을 사전 적용하고 `batch.cluster.sync.initialize-schema=false`로 설정합니다 (자동 생성은 `CREATE TABLE IF NOT EXISTS` 구문을 사용하므로 이를 지원하지 않는 DB 버전에서는 사용할 수 없음).
* 동기화 계정에는 두 테이블에 대한 `SELECT`, `INSERT`, `UPDATE`, `DELETE` 권한만 부여합니다.

##### [DDL: PostgreSQL 기준]
```sql
CREATE TABLE batch_journal_log (
    log_index    BIGINT        NOT NULL PRIMARY KEY,
    term         BIGINT        NOT NULL,
    entry_type   VARCHAR(32)   NOT NULL,
    request_id   VARCHAR(128),
    proposed_at  BIGINT        NOT NULL,
    payload      VARCHAR(4000),
    synced_at    TIMESTAMP     NOT NULL
);

CREATE TABLE batch_sync_checkpoint (
    cluster_id      VARCHAR(64)  NOT NULL PRIMARY KEY,
    last_log_index  BIGINT       NOT NULL,
    updated_at      TIMESTAMP    NOT NULL
);
```
* Oracle 환경에서는 `BIGINT` → `NUMBER(19)`, `VARCHAR` → `VARCHAR2`로 치환합니다.
