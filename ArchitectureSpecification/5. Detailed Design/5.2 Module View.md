#### 2. 패키지 의존 규칙

1. **하향 의존만 허용**: Bootstrap → Service → Consensus / Persistence → Domain Core 방향으로만 참조합니다. 하위 계층이 상위 계층을 참조하지 않으므로 패키지 간 순환 의존이 없습니다.
2. **결정론적 코어 격리**: `fsm`은 JDK 표준 컬렉션 외에 어떤 패키지도 참조하지 않습니다. 시계·디스크·네트워크·프레임워크 의존이 없으므로 "모든 노드가 동일한 로그를 동일한 순서로 apply하면 동일한 상태에 도달한다"는 결정론 원칙(5.3.2 공통 런타임 규약 2)이 코드 구조로 강제됩니다.
3. **프레임워크 의존 한정**: Spring 의존은 Bootstrap(자동 구성), `health`(Actuator), `sync`(`JdbcDatabaseStorage`의 Spring JDBC)에만 존재하며, Actuator와 Spring JDBC는 `compileOnly` 선택 의존입니다. `consensus`, `consensus.transport`, `storage`, `fsm`은 JDK 표준 API와 SLF4J만 사용하므로 Spring 컨텍스트 없이 단위 테스트와 가상 클러스터 테스트(7.1절)를 수행할 수 있습니다 (`CR-01`, `NR-01`, `QAS-08`).
4. **수요처 접점 최소화**: 수요처 모듈(`com.sds.batchservice.scheduler`)은 `api`의 In-Process API와 `recovery.ExecutionStatusProvider` SPI만 참조합니다. 합의·저장소 구현이 바뀌어도 수요처 코드는 변경되지 않습니다 (`DD-06`, `NR-03`).

#### 3. 순환 의존 제거: `storage` ↔ `consensus` 분리

초기 구현에서는 Write-Behind 관련 클래스가 `storage` 패키지에 함께 있어, `consensus`가 `storage.RaftLogManager`를 참조하고 `storage.WriteBehindSynchronizer`가 `consensus.RaftNode`를 참조하는 패키지 순환이 있었습니다. 이를 `sync` 패키지로 분리하여 제거했습니다.

| 구분 | 변경 전 | 변경 후 |
| :--- | :--- | :--- |
| 패키지 구성 | `storage`: `RaftLogManager`, `WriteBehindSynchronizer`, `DatabaseStorage`, `JdbcDatabaseStorage` | `storage`: `RaftLogManager`<br>`sync`: `WriteBehindSynchronizer`, `DatabaseStorage`, `JdbcDatabaseStorage` |
| 의존 관계 | `consensus` → `storage`, `storage` → `consensus` (순환) | `consensus` → `storage`, `sync` → `consensus`·`storage` (비순환) |
| `storage`의 외부 의존 | `consensus.RaftNode`, Spring JDBC | `fsm.LogEntry`만 참조 |

- **책임 분리**: 합의 경로의 로컬 영속화(전 노드, 모든 커밋 경로)와 리더 전용 비동기 DB 반영은 활성 조건·실행 주기·장애 영향이 서로 다릅니다. 분리 후에는 DB 관련 코드가 합의 코어의 컴파일 의존에 포함되지 않으므로, DB 장애 격리(`QAS-09`)가 런타임 구조(5.3.1 C&C)뿐 아니라 모듈 구조에서도 성립합니다.
- **변경 영향 축소**: DB 스키마·벤더 변경은 `sync`에, WAL 포맷 변경은 `storage`에 국한됩니다.
- **테스트 용이성**: `storage`는 합의 엔진 없이 단독 검증할 수 있고, `sync`는 `DatabaseStorage` Mock 구현(`MockDatabaseProxy`)으로 DB 장애를 주입해 검증합니다.
- 5.3.2 공통 런타임 규약의 계층 표기(`WriteBehindSynchronizer` = Sync 계층)와 패키지가 일치하게 되었습니다.

- **클래스**: 설계 결정(DD)의 메커니즘을 직접 구현하거나 패키지 간 접점이 되는 22개 클래스를 수록합니다. 내부 값 객체(record)·열거형·예외·빌더·설정 속성 클래스는 별첨에만 표기하며, 수요처 API의 반환 값인 `QueueLease`는 포함합니다.

- **관계**: 수록한 클래스 사이의 연관·합성·실현과 패키지 경계를 넘는 핵심 의존만 표기합니다. 중첩(⊕), 한정자 연관, 예외 발생(«throw»), 세부 생성 의존은 별첨에 표기합니다.

### 5.2.3 기존 분산 락 API 호환 (NR-05)

AS-IS BatchService는 Hazelcast `IMap.lock()` 기반 공통모듈 `DistributedLockExecutor`([[참고_Hazelcast를 활용한 distributed lock 공통모듈]])로 분산 락을 사용합니다. 수요처의 기존 호출 코드가 수정 없이 동작하도록(`NR-05`), `api.DistributedLockExecutor`는 AS-IS와 같은 클래스명, 메소드 시그니처, 락 의미를 유지합니다.

#### 1. API 대응

| 구분 | AS-IS (Hazelcast 공통모듈) | TO-BE (`batch-clustering-engine`) | 수요처 변경 |
| :--- | :--- | :--- | :--- |
| 클래스·Bean 등록 | `DistributedLockExecutor` (`@Component`) | `DistributedLockExecutor` (자동 구성 Bean, `@ConditionalOnMissingBean`) | 없음 (주입 코드 유지) |
| 락 실행 메소드 | `<T> T execute(String lockName, String logStr, Supplier<T> supplier)`<br>`void execute(String lockName, String logStr, Runnable runnable)` | 동일 시그니처 (두 번째 인자명 `ownerId`) | 없음 (호출 코드 유지) |
| 추가 메소드 | - | `execute(lockName, ownerId, waitMs, leaseMs, supplier)`, `acquire(lockName, owner, waitMs, leaseMs)` | 선택 사용 |
| 패키지 | AS-IS 공통모듈 패키지 | `com.sds.batchservice.cluster.api` | import 경로 변경 |
| 빌드 의존성 | Hazelcast | `batch-clustering-engine` JAR | 의존성 교체 |
| 클러스터 설정 | `spring.hazelcast.config`, `hazelcast.yaml`(`tcp-ip.member-list`) | `batch.cluster.*` 또는 환경변수 `RAFT_NODE_ID`, `RAFT_PEERS`, `RAFT_AUTH_TOKEN`, `WAL_DATA_DIR` (5.4.2) | 설정 교체 |

#### 2. 락 의미 대응

| 동작 | AS-IS (`IMap.lock()`) | TO-BE 구현 |
| :--- | :--- | :--- |
| 소유 단위 | 호출 스레드. `logStr`은 로그 출력에만 사용 | 소유자를 `{nodeId}:{threadId}:{ownerId}`로 기록합니다. 같은 `ownerId`를 넘기는 서로 다른 스레드도 서로 다른 소유자이므로 상호 배제됩니다. |
| 획득 대기 | 획득할 때까지 대기 | 기본 대기가 `WAIT_FOREVER`입니다. FSM의 FIFO 대기열에 등록된 뒤 승격될 때까지 대기하며, 대기 기한은 `LockStateMachine.saturatedAdd()`로 계산하여 오버플로를 방지합니다. |
| 재진입 | 같은 스레드의 재획득 허용, 획득 횟수만큼 해제 | 스레드별 `holdCounts`로 재진입 깊이를 관리합니다. 중첩 호출은 합의 명령 없이 실행하고, 가장 바깥 호출이 끝날 때 `LOCK_RELEASE`를 커밋합니다. |
| 임계 구역 예외 | 호출자에게 전파, 락 해제 | 동일 (`finally`에서 해제) |
| 소유 노드 장애 | 소유 멤버가 클러스터에서 이탈하면 해제 | lease(기본 10초) 만료 후 리더가 회수하고 다음 대기자를 승격합니다 (DD-02). |

#### 3. AS-IS와 다른 동작

- **대기 중 인터럽트**: AS-IS `IMap.lock()`은 인터럽트와 무관하게 대기하지만, TO-BE는 대기를 취소(`LOCK_CANCEL`)하고 `IllegalStateException`을 던집니다. 호출 스레드의 인터럽트 플래그는 유지됩니다.
- **과반수 노드 장애**: 커밋이 불가능하면 `LOCK_ACQUIRE` 커밋 대기 상한(`MAX_COMMIT_TIMEOUT_MS`, 60초) 후 `ClusterUnavailableException`을 던집니다. 상한은 Hazelcast 기본 operation call timeout(60초)과 같게 두었으며, 소수파에서 락을 부여하지 않는 것은 `QAS-03`의 요구입니다.
- **lease 상실**: 임계 구역 수행 중 lease 갱신이 거부되면 경고 로그를 남기고 임계 구역은 계속 실행되며, lease 만료 후 다른 대기자가 락을 획득할 수 있습니다. AS-IS도 소유 멤버가 네트워크 분할로 클러스터에서 분리되면 락이 해제되는 같은 한계가 있습니다.
- **로그 레벨**: 락 획득·해제 로그를 AS-IS의 INFO 대신 DEBUG로 기록합니다.

- 호환 동작은 `DistributedLockExecutorTest`(7.2.11)가 AS-IS 공통모듈의 테스트 절차를 옮겨 검증합니다.
