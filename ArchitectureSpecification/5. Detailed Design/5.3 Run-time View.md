### 5.3.1 Component & Connector View

본 절은 노드 1대(`batch-scheduler-N` Pod)의 JVM 프로세스 안에서 동작하는 런타임 컴포넌트와, 이들이 서로 또는 외부 요소와 상호작용하는 커넥터를 C&C(Component & Connector) 뷰로 정의합니다. 3노드 클러스터의 나머지 2대는 동일한 구성이므로 Raft Peer로 표기합니다. 컴포넌트 명칭은 5.3.2 공통 런타임 규약 1)과 동일하며, 구현 클래스는 5.2절 모듈 뷰의 패키지 구조를 따릅니다. 5.3.2의 시나리오는 본 절의 커넥터 위에서 진행되는 상호작용 순서를 기술합니다.

#### 3. 커넥터 카탈로그

커넥터 ID는 다이어그램의 커넥터 라벨과 대응합니다.

| ID | 커넥터 유형 | 요청·발행 측 (Out) → 제공·수신 측 (In) | 상호작용 | 동기성 및 구현 |
| :--- | :--- | :--- | :--- | :--- |
| C-01 | Procedure Call | Scheduler Core → Lock API | `execute(lockKey, owner, supplier)`로 DAG 판정 임계 구역 실행 | 동기. 획득·임계 구역·해제까지 호출 스레드 블로킹 |
| C-02 | Procedure Call | Scheduler Core → Queue API | `offer(jobId)` 후행 작업 적재 | 동기. 커밋 후 반환 |
| C-03 | Procedure Call | BatchLauncher → Queue API | `pollLease` · `renew` · `ack` · `requeue` | 동기. `leaseToken` 펜싱 |
| C-04 | Procedure Call | BatchLauncher → Journal API | `record(executionId, jobId, status, leaseToken)` | 동기. 커밋 후 반환 |
| C-05 | Procedure Call | Lock / Queue / Journal API → ConsensusEngine | `execute(Command, timeout)` | 동기(`CompletableFuture` 대기, 1회 최대 2,000ms). 팔로워면 C-12의 `ClientRequest`로 리더에 전달 |
| C-06 | Procedure Call | Cluster API → Multi-FSM | 로컬 뷰 조회 `get` · `isWaiting` · `isEmpty` · `awaitApply` | 동기. 읽기 전용 (상태 변경 경로 없음) |
| C-07 | Procedure Call | ConsensusEngine → Multi-FSM | `apply(LogEntry)`를 인덱스 순서로 호출 | 동기. 합의 락 보유 중 수행, 결과로 대기 중인 Future 완료 |
| C-08 | Procedure Call | ConsensusEngine → RaftLogManager | `append` · `sync` · `saveHardState` · `saveCommitIndex` | 동기. `sync()`는 합의 락 밖에서 수행 |
| C-09 | File I/O | RaftLogManager → Local WAL | 프레임 append, Group Commit `fsync`, HardState 원자적 교체, 기동 시 Replay | 동기 디스크 I/O |
| C-10 | Procedure Call | ConsensusEngine → P2P Transport | `send(Message)` | 비동기. 피어별 송신 큐에 적재 후 즉시 반환 |
| C-11 | Event Callback | P2P Transport → ConsensusEngine | `handleMessage(Message)` (등록된 수신자 호출) | `raft-io` 수신 스레드에서 통지 |
| C-12 | Raft RPC | P2P Transport ↔ Raft Peer | `PreVote` · `RequestVote` · `VoteResponse` · `AppendEntries` · `AppendResponse` · `ClientRequest` · `ClientResponse` | 비동기 메시지. TCP 7800, 피어별 영속 연결, `MAGIC`·nodeId·공유 토큰 핸드셰이크, 길이 프리픽스 프레임 |
| C-13 | Event Callback | ConsensusEngine → RecoveryCoordinator | `leadershipReady(term)` (`NO_OP` 커밋 시) | `raft-callback` 스레드에서 통지, 즉시 스캔 예약 |
| C-14 | Procedure Call | RecoveryCoordinator → ConsensusEngine | `LOCK_EXPIRE`, `QUEUE_REASSIGN`, `JOURNAL_RECORD`, `QUEUE_REQUEUE`, `QUEUE_ACK` 제안 | 동기. `recovery-worker` 스레드 |
| C-15 | Procedure Call | RecoveryCoordinator → Multi-FSM | 멤버십·락·in-flight·저널 스냅샷 조회 | 동기. 읽기 전용 |
| C-16 | Procedure Call (SPI) | RecoveryCoordinator → ExecutionStatusProvider Impl | `getStatus(executionId, jobId)` | 동기. 수요처 구현 호출 |
| C-17 | Event Callback | RecoveryCoordinator → BatchLauncher | `RecoveryAction` (`ADOPTED`, `REQUEUED`, `COMPLETED`, `LOCK_RECLAIMED`) | 등록된 Listener 통지 |
| C-18 | Procedure Call | WriteBehindSynchronizer → ConsensusEngine | `isLeaderReady` · `getCommitIndex` · `propose(SYNC_CHECKPOINT)` | 동기 조회, 비동기 제안 |
| C-19 | Procedure Call | WriteBehindSynchronizer → RaftLogManager | `slice(from, to, batchSize)` · `setCompactionFloor` | 동기. WAL 커밋 구간 판독 |

| C-24 | HTTP | ExecutionStatusProvider Impl → Execution Target | Job/Pod 상태 조회 (Kubernetes API, 5.4.2-5-2 RBAC) | 수요처 구현 |

#### 4. 동시성 및 스레드 모델

| 스레드 | 소유 컴포넌트 | 주기 / 트리거 | 수행 작업 | 동작 노드 |
| :--- | :--- | :--- | :--- | :--- |
| `raft-ticker-{nodeId}` | ConsensusEngine | 20ms 고정 주기 | Heartbeat 전송, Check-Quorum, 팔로워 무응답 판정(`MEMBER_STATUS` 제안), Election Timeout 시 PreVote 개시, 1초 주기 commitIndex 영속화 | 전 노드 |
| `raft-replicator-{nodeId}` | ConsensusEngine | 제안 신호 또는 Heartbeat 주기(500ms) | WAL Group Commit `fsync`, 커밋 판정, AppendEntries 전송 | 리더에서 동작 (팔로워는 대기) |
| `raft-callback-{nodeId}` | ConsensusEngine | 이벤트 | 리더 전달 요청(`ClientRequest`)의 응답 회신, 리더 확정 Listener 통지 | 전 노드 |
| `raft-io` (가변 풀) | P2P Transport | 연결 이벤트 | 연결 수락, 연결별 수신 루프(C-11 호출, 팔로워 `fsync` 포함), 피어별 송신 루프 | 전 노드 |
| `lock-renewer` (공유 1개) | Lock API | lease의 1/3 주기 | 임계 구역 수행 중인 락의 `LOCK_RENEW` 제안 | 락 보유 노드 |
| `recovery-scan-{nodeId}` | RecoveryCoordinator | 1초 고정 지연 + 리더 확정 이벤트 | 고립 작업·만료 락 판정 (리더가 아니면 즉시 반환) | 리더 |
| `recovery-worker-{nodeId}` | RecoveryCoordinator | 판정 결과 | SPI 상태 조회 및 복구 명령을 작업 단위로 순차 제안 | 리더 |
| `write-behind-{nodeId}` | WriteBehindSynchronizer | 200ms 고정 지연 (DB 장애 시 backoff) | DB 반영, Reconciliation, `SYNC_CHECKPOINT` 제안 | 리더 (팔로워는 `STANDBY`) |
| 호출자 스레드 | 수요처 | 수요처 로직 | Cluster API 호출 후 커밋·apply 결과까지 블로킹 | 전 노드 |

- **락 순서 고정**: ConsensusEngine의 합의 락 → Multi-FSM 모니터 → RaftLogManager 모니터 순서로만 획득하여 교착을 방지합니다.
- **락 밖 I/O**: 리더의 Group Commit `fsync`(C-08 `sync`)와 팔로워의 AppendEntries 응답 전 `fsync`는 합의 락을 놓은 상태에서 수행하고, 대기 중인 Future 완료와 Listener 통지도 락 밖에서 실행합니다. 디스크 지연이 선출·Heartbeat 처리를 막지 않습니다.
- **리더 전용 컴포넌트의 자기 억제**: RecoveryCoordinator와 WriteBehindSynchronizer는 모든 노드에서 스레드가 기동되지만 매 주기 `isLeaderReady()`를 확인하여 리더(현재 term `NO_OP` 커밋 완료)에서만 작업합니다. 리더 교체 시 별도 기동·종료 조정 없이 역할이 이전됩니다.

### 5.3.2 Scenario View (Sequence Diagram)

본 절은 3장(Architectural Driver), 4장(Top Level Design: DD-01 ~ DD-07), 5.1절(Conceptual Architecture), 5.4절(Deployment View)에서 결정된 핵심 메커니즘이 런타임 환경에서 어떻게 상호작용하는지 시퀀스 다이어그램으로 구체화합니다. 모든 시나리오는 아래 **공통 런타임 규약**을 전제로 하며, 시스템 라이프사이클과 장애 대응 유형에 따라 다음 5가지 핵심 시나리오로 분류하여 정의합니다.

- **Scenario 1: 정상 상태 분산 배치 스케줄링 및 Multi-FSM 실행 흐름** (`UC-01`, `QAS-01`, `QAS-02`, `DD-02`, `DD-03`, `DD-04`, `DD-05`, `DD-06`)
- **Scenario 2: 리더 노드 장애 감지, 신규 리더 선출 및 고립 작업 복구 흐름** (`UC-02`, `UC-03`, `UC-05`, `QAS-05`, `QAS-06`, `DD-01`, `DD-02`, `DD-03`, `DD-04`, `DD-05`)
- **Scenario 3: 일반 노드 장애 감지, 멤버십 자가 치유 및 Pod 재기동 재합류 흐름** (`UC-04`, `UC-05`, `QAS-04`, `DD-01`, `DD-05`, `DD-07`)

##### 2) Raft 로그 엔트리 및 FSM 명령 규약

- **엔트리 형식**: `{ index, term, type, payload, proposedAt, requestId }`
- **결정론 원칙**: FSM은 apply 시 로컬 시계(`System.currentTimeMillis()`)를 사용하지 않고, 리더가 제안 시점에 기록한 `proposedAt`만 사용합니다. 만료(lease/visibility timeout) 판정은 리더가 자신의 시계로 감지한 뒤 `LOCK_EXPIRE`, `QUEUE_REQUEUE` 명령을 **로그로 제안**하여 반영합니다.
- **리더 교체 시 lease 재설정**: `expireAt`, `deadline`은 해당 엔트리를 제안한 리더의 시계 기준이므로, 신규 리더의 `NO_OP`을 apply할 때 모든 락·in-flight 작업·대기자의 만료 시각을 `NO_OP.proposedAt + leaseMs`(`visibilityMs`, `waitMs`)로 재설정합니다. 만료 판정에 쓰이는 시각은 항상 현재 리더 1대의 시계에서 나오므로 노드 간 시간 동기화에 의존하지 않으며, 재설정으로 만료는 늦어질 수만 있고 앞당겨지지 않습니다. Raft 타이머(Heartbeat, Election Timeout, 장애 판정)는 단조 시계(`System.nanoTime()`)로 경과 시간을 측정합니다.
- **멱등성 원칙**: FSM은 `requestId`별 처리 결과를 보관하여, 리더 교체·타임아웃으로 인한 클라이언트 재시도 시 동일 결과를 반환합니다.
- **펜싱 토큰(Fencing Token)**: 락의 `fenceToken`은 커밋된 `LOCK_ACQUIRE` 엔트리의 `index`, 작업 인출의 `leaseToken`은 커밋된 `QUEUE_DEQUEUE`/`QUEUE_REASSIGN` 엔트리의 `index`를 사용합니다. 로그 인덱스는 클러스터 전체에서 단조 증가하므로 별도 발급기 없이 전역 유일성이 보장됩니다. 토큰이 현재 값과 일치하지 않는 갱신·해제·보고 명령은 FSM에서 거부됩니다.
- **락 소유자 식별자**: `owner = "{nodeId}:{threadId}:{ownerId}"` 형식으로 기록하여, 노드 장애 시 해당 노드가 보유한 락을 식별하고 같은 노드의 서로 다른 호출 스레드를 구분합니다. AS-IS Hazelcast 공통모듈의 스레드 단위 소유와 같은 의미입니다 (5.2.3).

| 도메인 | 명령 | 주요 payload | apply 결과 |
| :--- | :--- | :--- | :--- |
| Lock | `LOCK_ACQUIRE` | lockKey, owner, leaseMs, waitMs | `GRANTED`: `fenceToken`=entry index, `expireAt`=proposedAt+leaseMs / `QUEUED`: 점유 중이고 waitMs > 0이면 FIFO 대기열 등록 / `DENIED`: 점유 중이고 waitMs = 0 |
| Lock | `LOCK_RENEW` | lockKey, fenceToken, leaseMs | 토큰 일치 시 `expireAt` 연장 |
| Lock | `LOCK_RELEASE` | lockKey, fenceToken | 토큰 일치 시 해제 |
| Lock | `LOCK_EXPIRE` | lockKey, fenceToken | 리더 판정에 의한 만료·강제 회수 (토큰 일치 시) |
| Lock | `LOCK_CANCEL` | lockKey, ownerId | 대기 기한 초과 시 대기열에서 제거. 취소 직전에 승격되어 소유 중이면 해제 후 다음 대기자 승격 |
| Queue | `QUEUE_ENQUEUE` | jobId, front | 대기열 적재 (`front=true` 시 맨 앞, 동일 jobId 중복 적재 무시) |
| Queue | `QUEUE_DEQUEUE` | workerId, visibilityMs | **apply 시점에 FSM이 head를 결정**하여 in-flight `{jobId, workerId, deadline, leaseToken}` 등록 후 jobId 반환 (비어 있으면 EMPTY) |
| Queue | `QUEUE_RENEW` | jobId, leaseToken, visibilityMs | 토큰 일치 시 deadline 연장 |
| Queue | `QUEUE_ACK` | jobId, leaseToken | 토큰 일치 시 in-flight 제거 (처리 완료) |
| Queue | `QUEUE_REQUEUE` | jobId, reason, front | in-flight → 대기열 재적재 (`front=true` 시 최우선) |
| Queue | `QUEUE_REASSIGN` | jobId, newWorkerId | 실행 중 작업의 추적 노드 변경, 신규 `leaseToken` 발급 |
| Journal | `JOURNAL_RECORD` | executionId, jobId, status, executorNode, leaseToken | 실행 상태 전이 (`PENDING`→`RUNNING`→`COMPLETED`/`FAILED`) |
| Cluster | `NO_OP` | - | 신규 리더의 현재 term 엔트리 커밋 (이전 term 엔트리 확정), 락·in-flight 작업·대기자 만료 시각을 `proposedAt` 기준으로 재설정 |
| Cluster | `MEMBER_STATUS` | nodeId, ALIVE/DEAD | 활성 멤버십 갱신 (**Quorum 산정 분모는 불변**) |
| Cluster | `SYNC_CHECKPOINT` | lastDbSyncedIndex | 전 노드 WAL 압축 하한선(compaction floor) 동기화 |

##### 3) 노드 간 RPC 규약

모든 RPC는 단일 Raft TCP 포트(`7800/TCP`)의 노드 쌍별 영속 연결 위에서 길이 프리픽스 바이너리 프레임으로 교환하며, 연결 수립 시 클러스터 공유 토큰 핸드셰이크로 노드를 인증합니다(전송 구간 암호화는 5.4.2-5-1).

| RPC | 주요 필드 | 용도 |
| :--- | :--- | :--- |
| `PreVote` / `RequestVote` | term, candidateId, **lastLogIndex, lastLogTerm** | 선출 사전 확인 / 투표 요청 |
| `VoteResponse` | term, voteGranted | 투표 응답 |
| `AppendEntries` | term, leaderId, **prevLogIndex, prevLogTerm**, entries[], leaderCommit | 로그 복제. `entries`가 비어 있으면 Heartbeat |
| `AppendResponse` | term, success, matchIndex, conflictIndex | 복제 응답. 실패 시 `conflictIndex`로 역행 지점 힌트 제공 |
| `InstallSnapshot` | term, lastIncludedIndex, lastIncludedTerm, data chunk | 압축된 구간에 대한 스냅샷 전송. 로그 압축과 함께 적용할 후속 구현 과제이며(`RISK-01`) 현재 전송 계층(`Message.Type`)에는 포함되지 않음 |
| `ClientRequest` / `ClientResponse` | requestId, command(s) / status(`OK`, `NOT_LEADER(leaderHint)`, `TIMEOUT`), result | 팔로워 노드 API 요청의 리더 전달 및 결과 회신 |

**Flowchart 1. 후보의 리더 선출** (`RaftNode.startPreVoteLocked`, `startElectionLocked`, `handleVoteResponseLocked`, `becomeLeaderLocked`)

![[5.3.2 Raft Flowchart 1 - Candidate Election.svg]]

- **PreVote 선행**: Election Timeout이 만료되어도 곧바로 term을 올리지 않고, `currentTerm + 1`로 선출이 가능한지 먼저 확인합니다. 과반 승인을 받은 경우에만 term을 올리고 HardState를 `fsync`한 뒤 RequestVote를 보냅니다. 고립된 노드가 Timeout을 반복해도 term이 커지지 않으므로, 복귀 시 정상 리더를 강등시키지 않습니다(Scenario 5 4단계).
- **과반 판정**: 과반수 분모는 전체 노드 수(3)로 고정하며(불변식 6), 찬성은 자신이 요청한 term의 응답만 셉니다.
- **리더 전환**: 팔로워별 `nextIndex`를 자신의 `lastIndex + 1`로, `matchIndex`를 0으로 초기화하고 현재 term의 `NO_OP`을 즉시 복제합니다. 팔로워 로그가 뒤처지거나 다르면 Flowchart 3의 실패 응답 경로로 `nextIndex`가 맞춰집니다.

**Flowchart 2. 투표자의 PreVote / RequestVote 판정** (`RaftNode.handlePreVoteLocked`, `handleRequestVoteLocked`, `isUpToDateLocked`)

![[5.3.2 Raft Flowchart 2 - Vote Decision.svg]]

- **PreVote 판정**: term이 더 높고, 리더가 살아 있지 않으며, 후보 로그가 최신 이상일 때만 승인합니다. 최근 1,500ms 안에 리더 메시지를 받은 노드는 승인하지 않으므로, 일시적으로 지연된 노드 한 대가 정상 리더를 교체시키지 못합니다. PreVote는 상태를 바꾸지 않으므로 `fsync`하지 않습니다.
- **RequestVote 판정**: 한 term에서 한 후보에게만 투표하고(`votedFor`), 투표 사실을 응답 전에 `fsync`합니다(불변식 4). 재기동 후 같은 term에서 다른 후보에게 다시 투표하는 이중 투표를 막습니다. 응답이 유실되어 같은 후보가 다시 요청하면 다시 승인합니다.
- **로그 최신성 (불변식 5)**: 마지막 엔트리의 term을 먼저 비교하고, term이 같으면 마지막 index를 비교합니다. 커밋된 엔트리는 과반 노드에 있으므로, 과반의 표를 얻은 후보는 모든 커밋 엔트리를 가집니다. Flowchart 4에서 팔로워가 커밋된 엔트리를 절단하는 경우가 생기지 않는 근거가 됩니다.

**로그 최신성 판정 예시** (Flowchart 2의 ★)

| 후보 (lastLogIndex:lastLogTerm) | 투표자 (lastIndex:lastTerm) | 판정 | 근거 |
| :--- | :--- | :--- | :--- |
| `5:3` | `7:2` | 최신 이상 (승인 가능) | 후보의 마지막 term(3)이 더 높으므로 로그가 짧아도 최신 |
| `6:3` | `7:3` | 뒤처짐 (거절) | 마지막 term이 같고 후보의 마지막 index(6)가 더 작음 |
| `7:3` | `7:3` | 최신 이상 (승인 가능) | 마지막 term·index가 모두 같음 |

**Flowchart 3. 리더의 AppendEntries 송신 및 AppendResponse 처리** (`RaftNode.replicateToLocked`, `handleAppendResponseLocked`, `advanceCommitLocked`)

![[5.3.2 Raft Flowchart 3 - Leader Replication and AppendResponse.svg]]

- **송신**: 팔로워별 `nextIndex`로 `prevLogIndex = nextIndex − 1`과 그 위치의 term을 채워 보냅니다. 응답을 기다리는 동안에는 이미 보낸 구간 다음부터 이어 보내고(파이프라이닝), Heartbeat 주기마다 확인되지 않은 구간을 `nextIndex`부터 다시 보냅니다.
- **실패 응답 (`nextIndex` 역행)**: `conflictIndex`를 힌트로 `nextIndex`를 되돌리고 즉시 재전송합니다. `matchIndex`까지는 팔로워가 `fsync` 후 확인한 구간이므로 `nextIndex`는 `matchIndex + 1` 아래로 내려가지 않습니다. 일치 지점을 찾을 때까지 이 과정을 반복하며, 일치하면 팔로워는 그 뒤의 충돌 구간을 절단하고 리더 로그로 교체합니다.
- **성공 응답 (커밋 판정)**: `matchIndex`를 갱신한 뒤, 과반 노드가 가진 index 중 **현재 term의 엔트리**만 커밋합니다(불변식 2). 이전 term 엔트리는 과반에 복제되어 있어도 직접 커밋하지 않고, 신규 리더의 `NO_OP`이 커밋될 때 함께 확정됩니다(Scenario 2 3단계). 이전 term 엔트리를 복제 수만으로 커밋하면, 그 엔트리가 없는 노드가 더 높은 term의 로그로 리더가 되어 커밋된 엔트리를 덮어쓸 수 있기 때문입니다.
- **상위 term 응답**: 응답의 term이 더 높으면 다른 리더가 선출된 것이므로 Follower로 강등하고 대기 중인 요청을 `NOT_LEADER`로 실패시킵니다.

**Flowchart 4. 팔로워의 AppendEntries 처리** (`RaftNode.handleAppendEntriesLocked`)

![[5.3.2 Raft Flowchart 4 - Follower AppendEntries.svg]]

- **term 확인**: 더 높은 term이면 HardState를 `fsync`한 뒤 그 리더를 따르고, 더 낮은 term(구 리더)이면 자신의 `currentTerm`을 담아 거절합니다. 이 응답을 받은 구 리더는 Flowchart 3에서 스스로 강등합니다.
- **로그 일관성 검사 (`prevLogIndex`, `prevLogTerm`)**: 리더가 보낸 엔트리 바로 앞 위치(`prevLogIndex`)에 같은 term(`prevLogTerm`)의 엔트리가 있어야 이어 붙입니다. 두 로그가 같은 index에 같은 term의 엔트리를 가지면 그 index까지의 로그 전체가 같다는 Raft의 Log Matching 속성에 따라, 전체 로그를 비교하지 않고 이 한 지점만 확인합니다.
  - 로컬 로그가 `prevLogIndex`보다 짧으면 `conflictIndex = lastIndex + 1`을 응답하여, 리더가 로컬 로그 끝 다음부터 다시 보내게 합니다.
  - 같은 위치의 term이 다르면 로컬에서 그 term이 시작된 첫 index를 `conflictIndex`로 응답하여, 리더가 충돌한 term 구간을 한 번에 건너뛰게 합니다. 엔트리를 1개씩 역행하는 왕복을 줄입니다.
- **엔트리 병합**: 검사를 통과하면 `entries`를 로컬 로그와 비교하여 이미 가진 엔트리(같은 index·term)는 건너뛰고, 처음 달라지는 엔트리부터 반영합니다. 같은 index에 다른 term이 있으면 미커밋 충돌 구간이므로 그 지점 이후를 절단하고 append합니다. 충돌이 없으면 절단하지 않으므로, 늦게 도착한 이전 AppendEntries가 이미 받은 뒤쪽 엔트리를 지우지 않습니다.
  - 절단 지점이 `commitIndex` 이하이면 절단하지 않고 거절하는 방어 로직을 둡니다. 커밋 규칙(불변식 2)과 로그 최신성 투표(불변식 5, Flowchart 2)가 지켜지는 한 이 경로는 발생하지 않습니다.
- **커밋 반영과 응답**: `commitIndex`는 `leaderCommit`과 이번 메시지로 리더와 일치가 확인된 마지막 index(`prevLogIndex + entries 수`) 중 작은 값까지만 올립니다. 새로 append한 엔트리가 있으면 합의 락을 놓고 `fsync`한 뒤에 성공을 응답합니다(불변식 1).

##### 5) 핵심 불변식 (Safety Invariants)

1. **영속 후 계수**: 리더·팔로워 모두 WAL `fsync` 완료 후에만 해당 엔트리의 복제 성공으로 계수합니다.
2. **커밋 규칙**: 과반수 노드의 `matchIndex ≥ N`이고 `log[N].term == currentTerm`일 때만 `commitIndex = N`으로 전진합니다.
3. **선반영 금지**: 큐 인출을 포함한 모든 상태 변경은 커밋 후 apply된 결과만 클라이언트에 반환합니다. 리더 FSM에 먼저 반영한 뒤 복제하는 경로는 두지 않습니다.
4. **투표 영속화**: `currentTerm`, `votedFor`는 투표 응답·RequestVote 송신 전에 `fsync`합니다.
5. **로그 최신성 투표**: 후보의 `(lastLogTerm, lastLogIndex)`가 자신보다 같거나 최신일 때만 투표합니다.
6. **Quorum 고정**: 과반수 산정 분모는 설정된 전체 노드 수(3)로 고정합니다. 장애 노드를 멤버십에서 제외해도 과반수 기준을 축소하지 않습니다.
7. **Check-Quorum / 로컬 조회**: 리더는 Election Timeout 동안 과반수 응답을 받지 못하면 스스로 Follower로 강등합니다. 상태 판정을 위한 조회는 로컬 FSM 뷰를 사용하되, 판정의 근거가 되는 명령(예: `LOCK_ACQUIRE`)을 커밋한 뒤 로컬 FSM이 해당 인덱스까지 apply되었음을 확인하고 수행합니다(Scenario 1 1단계). 리더십을 별도로 확인하는 선형화 읽기(ReadIndex)는 제공하지 않으므로, 커밋을 거치지 않은 단독 조회는 최신 커밋을 반영하지 않을 수 있습니다.
8. **압축 하한**: 로그 압축 구현 시(후속 과제, `RISK-01`) WAL 압축은 `min(snapshotIndex, lastDbSyncedIndex)` 이전 구간에만 허용합니다. 현재는 `SYNC_CHECKPOINT`로 압축 하한선(`compactionFloor`)만 관리합니다.

#### 1. Scenario 1: 정상 상태 분산 배치 스케줄링 및 Multi-FSM 실행 흐름

##### 1) 개요 및 사전 조건
- **목적**: 정기 배치 트리거 시 DAG 상태 전이의 원자적 판정(분산 락), 작업 적재·인출(분산 큐), 실행 상태 저널링, 실행 위임 및 완료 처리, Write-Behind 비동기 RDBMS 반영까지의 정상 오케스트레이션 라이프사이클을 정의합니다.
- **사전 조건**: 3개 노드 클러스터가 정상 구동 중(Node 1: Leader, Node 2/3: Follower, term=1, commitIndex=100)이며, 메타 DB 커넥션이 정상이고 DB 체크포인트는 `last_log_index=100`입니다.
- **설계 포인트 (분산 락 적용 범위)**:
  - **락 보유 구간 = DAG 선후행 판정 + 후행 작업 적재**: "선행 작업 완료 확인 → 후행 작업 미적재 확인 → 적재"는 여러 노드가 동시에 수행할 수 있는 읽기-판정-쓰기(Read-Modify-Write)이므로, 이 **짧은 임계 구역(수~수십 ms)** 에만 분산 락을 사용합니다.
  - **락 키 단위**: `dag:{workflowId}` 단위로 잠가, 서로 무관한 워크플로우 간 대기를 배제합니다.
  - **판정 데이터 원천**: 판정은 메타 DB가 아닌 **로컬 Multi-FSM(Journal/Queue)** 을 조회합니다. 메타 DB는 Write-Behind로 지연 반영(평시 약 200ms, DB 장애 시 무기한)되므로 판정 원천으로 사용하지 않습니다.
  - **락 밖 구간(인출·실행·모니터링·상태 기록)**: 락을 보유하지 않습니다. 실행 배타성은 큐 in-flight 할당과 `leaseToken` 펜싱으로, 상태 기록 순서는 Raft 로그 순서로 보장하며, `BatchLauncher`는 메타 DB에 직접 기록하지 않습니다. 이를 통해 장시간 배치 실행 중 락 lease 갱신 실패로 상호 배제가 깨지는 문제를 배제합니다.

##### 3) 단계별 제어 흐름
1. **DAG 선후행 판정 임계 구역 (분산 락, QAS-01)**:
   - `Timer`가 워크플로우(`wf-001`) 스케줄을 트리거하거나 선행 작업 완료 이벤트(4단계)가 발생하면, `Scheduler Core`가 워크플로우 단위 락 키로 `DistributedLockExecutor.execute(lockName="dag:wf-001", ownerId="trg-7781", waitMs, leaseMs=5000, supplier)`를 호출합니다. 락 소유자는 `node-1:{threadId}:trg-7781`로 기록됩니다.
   - 리더의 `ConsensusEngine`은 `LOCK_ACQUIRE` 엔트리(index=101)를 `RaftLogManager`에 `fsync` 기록하고, 팔로워에 `AppendEntries(prevLogIndex=100, prevLogTerm=1, entries=[101])`를 병렬 전송합니다.
   - 팔로워는 `prevLog` 일치를 확인한 후 append + `fsync`하고 `AppendResponse(matchIndex=101)`를 응답합니다.
   - 과반수(리더 포함 2/3) `matchIndex ≥ 101`이고 해당 엔트리가 현재 term이면 `commitIndex=101`로 전진하고, `LockStateMachine`에 apply하여 `fenceToken=101`을 발급합니다.
   - 임계 구역에서는 로컬 FSM이 `fenceToken`(=101) 이상까지 apply되었음을 확인한 뒤 **로컬 FSM을 조회**하여 판정합니다. 락 획득 이전에 커밋된 완료 보고는 모두 판정에 반영되고, 락 획득 이후 커밋된 완료 보고는 별도의 완료 이벤트로 락을 다시 획득하여 재판정하므로 판정 누락이 없습니다.
     - (a) 선행 Task A의 저널 상태가 `COMPLETED`인지 확인합니다.
     - (b) 후행 Task B가 대기열·in-flight에 없고 해당 스케줄 회차의 실행 기록도 없는지 확인합니다.
   - (a), (b)를 모두 만족하면 후행 Task B를 스케줄 회차가 포함된 결정론적 jobId(`Job_101` = `wf-001:taskB:{scheduledTime}` 형식)로 `QUEUE_ENQUEUE`(index=102) 적재합니다. FSM의 동일 jobId 중복 적재 무시는 대기·in-flight 중에만 유효하고 `QUEUE_ACK` 이후에는 적용되지 않으므로, (b) 확인은 반드시 락 안에서 수행합니다.
   - 적재 후 즉시 `LOCK_RELEASE(fenceToken=101)`(index=103)로 락을 반환합니다. 각 명령은 동일한 복제·커밋 절차를 거치며, 임계 구역 수행 중에는 `DistributedLockExecutor`가 lease(5,000ms)의 1/3 주기로 `LOCK_RENEW`를 자동 제안합니다.
2. **분산 큐 작업 인출 (QAS-02)**:
   - 워커 노드(`Node 2`)의 `BatchLauncher`가 `DistributedQueueService.pollLease()`를 호출하면, `Cluster API`가 `QUEUE_DEQUEUE(workerId="node-2", visibilityMs=30000)` 명령을 생성합니다. 로컬 노드는 팔로워이므로 `ClientRequest(requestId, QUEUE_DEQUEUE)`로 리더에 전달합니다.
   - 리더는 `QUEUE_DEQUEUE` 엔트리(index=104)를 복제·커밋한 **후** `QueueStateMachine`에 apply합니다. FSM은 apply 시점에 대기열 head(`Job_101`)를 결정하여 in-flight `{worker=node-2, deadline=proposedAt+30s, leaseToken=104}`로 등록하고 결과를 반환합니다.
   - 리더는 `ClientResponse(OK, "Job_101", leaseToken=104)`를 회신합니다. 피크 타임의 동시 인출 요청은 Group Commit으로 묶어 1회 `fsync`·1회 AppendEntries로 처리합니다.
3. **실행 위임 및 저널링**:
   - `BatchLauncher`는 `Execution Target`에 `launch(executionId="exec-101", leaseToken=104)`를 요청하고, 기동 확인 후 `JOURNAL_RECORD(exec-101, RUNNING, executorNode=node-2, leaseToken=104)`(index=105)를 제안합니다.
   - 실행이 lease 갱신 주기(10초)를 초과하면 `QUEUE_RENEW(leaseToken=104)`를 주기적으로 제안하여 deadline을 연장합니다.
   - 이 구간은 분산 락을 보유하지 않습니다. 상태 변경은 `JOURNAL_RECORD`로만 보고하며 메타 DB에는 직접 기록하지 않습니다(5단계 Write-Behind).
   - `QUEUE_RENEW` 또는 `JOURNAL_RECORD`가 토큰 불일치로 거부되면, 해당 작업이 재할당·재적재되어 소유권을 상실한 것으로 판단하고 상태 보고를 중단합니다. 이후 처리는 리더의 `RecoveryCoordinator`가 판정합니다(Scenario 2).
4. **작업 완료 처리**:
   - `Execution Target`의 종료(`exitCode=0`)가 감지되면, `BatchLauncher`는 `JOURNAL_RECORD(exec-101, COMPLETED)`와 `QUEUE_ACK(Job_101, leaseToken=104)`를 하나의 요청으로 제안합니다(index=106~107).
   - 커밋·apply 후 `Scheduler Core`는 로컬 Multi-FSM 조회(C-06, `awaitApply`)로 선행 작업 완료 반영을 확인하고, 후행 DAG 판정을 1단계부터 반복합니다.
   - 리더는 후속 Heartbeat(`AppendEntries(entries=[], leaderCommit=107)`)로 커밋 인덱스를 전파하여, 모든 팔로워가 동일 인덱스까지 apply하도록 수렴시킵니다.
5. **Write-Behind 비동기 RDBMS 반영**:
   - 리더의 `WriteBehindSynchronizer`는 200ms 주기로 `ConsensusEngine`의 commitIndex를 조회하여(C-18) DB 체크포인트 이후의 커밋 구간을 확인합니다. 별도 메모리 버퍼를 두지 않고 엔트리 데이터는 WAL에서 판독합니다.
   - `RaftLogManager`에서 커밋 구간(101~107)을 최대 500건 단위로 판독하여(C-19), 단일 DB 트랜잭션으로 `batch_journal_log`의 해당 `log_index` 구간 삭제 후 일괄 INSERT(재반영 시 멱등)와 `batch_sync_checkpoint.last_log_index=107` 갱신을 함께 커밋합니다.
   - 커밋 성공 후 WAL 압축 하한선을 107로 갱신하고, `SYNC_CHECKPOINT`를 제안하여 전 노드의 압축 하한선을 동기화합니다.

#### 2. Scenario 2: 리더 노드 장애 감지, 신규 리더 선출 및 고립 작업 복구 흐름

##### 1) 개요 및 사전 조건
- **목적**: 활성 리더 노드의 비정상 종료(Crash) 시 3초 이내 신규 리더 자동 선출(`QAS-05`)과, 장애 노드가 추적하던 미완료 작업을 10초 이내에 **중복 실행 없이** 식별·복구(`QAS-06`)하는 절차를 정의합니다.
- **사전 조건**: 3개 노드 클러스터(term=1, lastLogIndex=commitIndex=107)에서 Node 1(Leader)의 `BatchLauncher`가 `exec-101`(`Job_101`, leaseToken=104)을, Node 3의 `BatchLauncher`가 `exec-102`를 각각 추적 중일 때 Node 1이 강제 종료(Crash)됩니다. `exec-101`의 Execution Target Pod(`ns-batch`)는 별도 노드에서 계속 구동 중일 수 있습니다.
- **설계 포인트**:
  - 신규 리더는 **자기 term의 `NO_OP` 엔트리를 먼저 커밋**하여 이전 term의 커밋 엔트리를 모두 확정·apply한 후에 복구 판정을 시작합니다.
  - 복구 조치(락 회수, 저널 전이, 재적재)는 FSM을 직접 수정하지 않고 **모두 로그 엔트리로 제안**하여 전 노드 FSM 일관성을 유지합니다.
  - 리더 장애와 작업 실행 장애를 구분합니다. 실행 추적 노드가 생존한 작업은 조치하지 않고, 추적 노드가 장애인 작업만 Execution Target 상태 조회 후 인수·재적재·완료 처리합니다.

##### 2) 참여 컴포넌트 (Lifeline)

| 구분 | 참여 컴포넌트 (Lifeline) | 분류 / 계층 매핑 | 역할 및 주요 책임 |
| :--- | :--- | :--- | :--- |
| **장애 대상** | `Node 1 (구 Leader)` | Cluster Member [Crash Node] | Heartbeat 송신이 중단된 구 리더 (exec-101 추적 노드) |
| **신규 리더** | `Node 2 ConsensusEngine` | Raft Core (`com.sds.batchservice.cluster.consensus`) | Election Timeout 감지, PreVote/RequestVote, 리더 승격, `NO_OP`·복구 명령 커밋 |
| **영속 스토리지** | `Node 2 RaftLogManager (WAL)` | Local WAL (`com.sds.batchservice.cluster.storage`) | HardState(`currentTerm`, `votedFor`) 및 엔트리 `fsync` |
| **상태 머신** | `Node 2 Multi-FSM` | FSM (`com.sds.batchservice.cluster.fsm`) | 커밋 엔트리 apply, 미완료 실행·in-flight 조회 제공 |

| **워커 노드** | `Node 3 BatchLauncher` | Application (`com.sds.batchservice.scheduler`) | 리더 전환 시 동일 `requestId`로 재시도, 재적재 작업 인출·실행 |

##### 3) 단계별 제어 흐름
1. **리더 장애 및 Election Timeout 감지 (2초 이내)**:
   - Node 1이 Crash되어 Heartbeat(500ms 주기) 송신이 중단됩니다.
   - Node 2의 Election Timer(1,500~2,000ms 난수, 예: 1,620ms)가 먼저 만료됩니다.
2. **PreVote 및 신규 리더 선출 (선출 단계 1초 이내, 총 3초 이내)**:
   - Node 2는 term을 올리기 전에 `PreVote(term=2, lastLogIndex=107, lastLogTerm=1)`를 전송합니다. Node 3은 최소 Election Timeout(1.5초) 동안 리더 메시지를 받지 못했고 후보 로그가 최신이므로 승인합니다.
   - Node 2는 `Candidate`로 전환하여 `currentTerm=2`, `votedFor=node-2`를 WAL에 `fsync`한 뒤 `RequestVote(term=2, lastLogIndex=107, lastLogTerm=1)`를 전송합니다.
   - Node 3은 term(2 > 1), 미투표 여부, 로그 최신성을 검증하고 HardState를 `fsync`한 후 `voteGranted=true`를 응답합니다.
   - Node 2는 과반수(2/3) 득표로 `Leader`로 승격하고 `nextIndex[*]=108`로 초기화합니다.
3. **리더십 확정 및 멤버십 갱신**:
   - 신규 리더는 `NO_OP`(index=108, term=2)을 복제·커밋하여 이전 term 엔트리(~107)를 확정하고 `applyUpTo(108)`을 수행한 후 서비스를 개시합니다.
   - Node 1의 마지막 수신 시점으로부터 2초가 경과하면 `MEMBER_STATUS(node-1, DEAD)`(index=109)를 커밋합니다.
   - Node 3의 `BatchLauncher`는 구 리더 대상 요청이 실패하면 `leaderHint=node-2`로 **동일 `requestId`** 를 재전송하며, FSM의 `requestId` 멱등성으로 중복 반영이 방지됩니다.
4. **고립(Orphan) 작업 판정 및 복구 (리더 승격 후 10초 이내)**:
   - `RecoveryCoordinator`가 FSM에서 `RUNNING` 저널 및 in-flight 항목을 조회합니다.
     - `exec-102`: 추적 노드(node-3)가 ALIVE이고 lease가 유효하므로 **조치하지 않습니다** (중복 실행 방지).
     - `exec-101`: 추적 노드(node-1)가 DEAD이므로 고립 작업 후보로 판정하고 `Execution Target`에 실행 상태를 조회합니다.
   - 조회 결과에 따라 다음 명령을 **로그로 제안**합니다.
     - `RUNNING`: `QUEUE_REASSIGN(Job_101 → node-2)` + `JOURNAL_RECORD(executorNode=node-2)` — 재실행 없이 추적만 인수합니다.
     - `FAILED`/`NOT_FOUND`: node-1 소유 락에 대한 `LOCK_EXPIRE` + `JOURNAL_RECORD(PENDING)` + `QUEUE_REQUEUE(Job_101, front=true)` — 대기열 최우선으로 재적재합니다.
     - `COMPLETED`: `JOURNAL_RECORD(COMPLETED)` + `QUEUE_ACK` — 완료로 확정합니다.
5. **작업 정상 재분배 및 펜싱**:
   - 재적재된 경우 Node 3의 `BatchLauncher`가 `QUEUE_DEQUEUE`로 `Job_101`을 신규 `leaseToken=113`과 함께 인출하여 재실행합니다.
   - 구 실행분의 뒤늦은 보고(leaseToken=104)는 현재 토큰과 불일치하므로 FSM에서 거부됩니다.

#### 3. Scenario 3: 일반 노드 장애 감지, 멤버십 자가 치유 및 Pod 재기동 재합류 흐름

##### 1) 개요 및 사전 조건
- **목적**: 일반 멤버(Follower) 노드 장애 시 3초 이내 활성 멤버십에서 제외하고 잔여 노드에 동기화(`QAS-04`)하며, StatefulSet에 의해 재기동된 Pod가 전용 PVC의 WAL로 상태를 복원한 뒤 클러스터에 재합류하는 절차(`DD-05`, `DD-07`)를 정의합니다.
- **사전 조건**: 3개 노드 클러스터(Node 1: Leader)에서 Node 3(`batch-scheduler-2`, matchIndex=200)이 강제 종료(Crash)됩니다.
- **설계 포인트**:
  - 장애 감지는 리더가 **팔로워별 마지막 AppendResponse 수신 시각**으로 판정합니다(Heartbeat는 리더→팔로워 단방향이므로 응답 기준 판정이 필수).
  - 멤버십 변경은 `MEMBER_STATUS` 로그 엔트리로 커밋하여 잔여 노드에 동기화하며, Quorum 산정 분모(3)는 변경하지 않습니다.
  - 정상 종료(`UC-05`)도 종료 노드가 응답을 멈춘다는 점에서 같은 절차로 활성 멤버십에서 제외되며, 종료 전에 해제하지 못한 락과 추적 작업은 리더의 `RecoveryCoordinator`가 Scenario 2의 4단계로 처리합니다. 종료 노드가 리더이면 Scenario 2의 1~3단계로 재선출됩니다.
  - 노드 추가·노드 수 변경(`UC-04`)은 동적 멤버십 변경이 아닌 `RAFT_PEERS` 갱신과 전체 재배포로 수행하며(5.4.2-1), 기동한 노드는 본 시나리오 3~5단계와 같은 절차로 클러스터에 참여합니다.

##### 2) 참여 컴포넌트 (Lifeline)

| 구분 | 참여 컴포넌트 (Lifeline) | 분류 / 계층 매핑 | 역할 및 주요 책임 |
| :--- | :--- | :--- | :--- |
| **리더** | `Node 1 (Leader) ConsensusEngine` | Raft Core (`com.sds.batchservice.cluster.consensus`) | 팔로워별 응답 시각 추적, 장애 판정, `MEMBER_STATUS` 커밋, 재합류 노드 로그 보충 |
| **상태 머신** | `Node 1 Multi-FSM` | FSM (`com.sds.batchservice.cluster.fsm`) | 활성 멤버십 반영, 작업 분배 대상 갱신 |
| **팔로워** | `Node 2 ConsensusEngine + WAL` | Raft Core / Local WAL | 멤버십 엔트리 복제 및 Quorum 형성 |
| **장애 노드** | `Node 3 (batch-scheduler-2)` | Cluster Member | Crash 후 재기동, WAL Replay, 로그 따라잡기 |
| **인프라** | `K8s StatefulSet Controller` | Kubernetes (`DD-07`) | 동일 식별자 Pod 재생성 |
| **스토리지** | `PVC wal-storage-batch-scheduler-2` | RWO 전용 볼륨 (`DD-05`, `DD-07`) | 기존 WAL(`raft.log`)과 HardState 보존 |

##### 3) 단계별 제어 흐름
1. **장애 감지 (2초 이내)**:
   - Node 1(Leader)은 500ms마다 Heartbeat를 전송하고 팔로워별 마지막 `AppendResponse` 수신 시각을 갱신합니다.
   - Node 3의 응답이 2,000ms(Heartbeat 4회) 동안 없으면 로컬에서 DEAD로 판정합니다.
2. **멤버십 갱신 및 동기화 (1초 이내, 총 3초 이내)**:
   - 리더는 `MEMBER_STATUS(node-3, DEAD)`(index=201)를 Node 2와 복제·커밋하고, 전 노드 FSM의 활성 멤버십을 `[node-1, node-2]`로 갱신합니다.
   - `Scheduler Core`는 Node 3을 작업 분배 대상에서 제외하며, Node 3이 추적하던 실행 작업에는 Scenario 2의 4단계(고립 작업 판정) 절차를 적용합니다.
   - 과반수 분모는 3으로 유지되므로, Node 1 + Node 2(2/3)로 쓰기 합의가 계속됩니다.
3. **Pod 재생성 및 로컬 상태 복원**:
   - StatefulSet 컨트롤러가 동일 식별자(`batch-scheduler-2`)로 Pod를 재생성하고, 기존 PVC(`wal-storage-batch-scheduler-2`)를 `/var/data/batch/wal`에 재마운트합니다.
   - `RaftLogManager`는 HardState를 복원하고 `raft.log`(1~200)를 CRC 검증하며 Replay하여 영속화된 commitIndex까지 Multi-FSM을 복원합니다(5.4.2-3). Follower로 기동하며 따라잡기 전까지 Readiness는 `false`입니다.
4. **로그 따라잡기 (Catch-up)**:
   - 리더는 `nextIndex[node-3]` 기준으로 `AppendEntries(prevLogIndex=200, prevLogTerm=1, entries=[201..230])`를 전송합니다.
   - `prevLog` 불일치(WAL 꼬리 유실 등) 시 Node 3은 `conflictIndex`를 회신하고, 리더는 해당 지점부터 재전송합니다(공통 런타임 규약 4의 Flowchart 3·4, 케이스 3).
   - 로그 압축이 구현되지 않았으므로 리더는 전체 로그를 보유하며 `AppendEntries`만으로 따라잡습니다. 압축 구현 후 필요한 구간이 이미 압축된 경우에는 `InstallSnapshot`을 전송합니다(후속 구현 과제, `RISK-01`).
5. **재합류 확정**:
   - `matchIndex[node-3]`가 `commitIndex`에 도달하면 리더는 `MEMBER_STATUS(node-3, ALIVE)`를 커밋하고, Node 3은 Readiness를 `true`로 전환하여 작업 분배 대상에 복귀합니다.

#### 4. Scenario 4: 메타 DB 장기 장애 격리 및 복구 시 Reconciliation 동기화 흐름

##### 1) 개요 및 사전 조건
- **목적**: 메타 RDBMS 장애 중에도 Raft 합의와 로컬 WAL만으로 분산 락·큐·저널을 무중단 운영(`QAS-09`, 중단 시간 0초)하고, DB 복구 후 WAL에 보존된 미반영 구간을 30초 이내에 유실·중복 없이 재생(Replay)하여 최종 정합성을 복원하는 절차를 정의합니다.
- **사전 조건**: 3개 노드 클러스터가 정상 구동 중이며, DB 체크포인트는 `last_log_index=300`입니다.
- **설계 포인트**:
  - 동기화 기준점(`lastDbSyncedIndex`)은 노드 메모리가 아닌 **DB의 `batch_sync_checkpoint`를 원천**으로 하여, 리더 교체·재기동 후에도 정확한 지점부터 재개합니다.
  - 이력 반영과 체크포인트 갱신을 **단일 트랜잭션**으로 커밋하고, 반영 구간의 기존 `log_index` 행을 삭제한 뒤 삽입하여 같은 구간을 다시 반영해도 결과가 같으므로, 트랜잭션 도중 장애·리더 교체 시에도 멱등성을 보장합니다.
  - DB 장애 중에는 압축 하한선이 체크포인트에 고정되어 미반영 구간의 WAL이 보존됩니다(5.4 PVC 사이징: 7일 보존 약 280MB).
  - K8s Readiness Probe는 DB Health를 포함하지 않아, DB 장애가 스케줄러 Pod 트래픽 차단으로 전파되지 않습니다.

##### 2) 참여 컴포넌트 (Lifeline)

| 구분 | 참여 컴포넌트 (Lifeline) | 분류 / 계층 매핑 | 역할 및 주요 책임 |
| :--- | :--- | :--- | :--- |
| **클라이언트** | `Scheduler Core / BatchLauncher` | Application (`com.sds.batchservice.scheduler`) | DB 장애와 무관하게 락·큐·저널 오퍼레이션 요청 |
| **코어 엔진** | `Node 1 (Leader) Cluster API + ConsensusEngine` | API / Raft Core | DB I/O 없이 합의·커밋·apply 처리 |
| **팔로워** | `Node 2, 3 ConsensusEngine + WAL` | Raft Core / Local WAL | 복제 및 Quorum 형성 |

| **교체 리더** | `Node 2 WriteBehindSynchronizer` | Sync (`com.sds.batchservice.cluster.sync`) | 동기화 중 리더 교체 시 DB 체크포인트로부터 재개 |

##### 3) 단계별 제어 흐름
1. **DB 장애 감지 및 격리**:
   - `WriteBehindSynchronizer`의 일괄 반영 트랜잭션이 `SQLException`/커넥션 타임아웃으로 실패하면 트랜잭션을 롤백하고 상태를 `DB_DOWN`으로 전환합니다.
   - 재시도는 1s → 2s → 4s → 8s → 10s(상한) backoff로 수행하며, WAL 압축 하한선은 체크포인트(300)에 고정됩니다.
2. **무중단 분산 오케스트레이션 지속**:
   - `Scheduler Core`와 `BatchLauncher`의 락·큐·저널 요청은 Scenario 1과 동일하게 WAL `fsync` → Quorum 복제 → 커밋 → apply 경로로 처리되며, 이 경로에는 DB I/O가 없으므로 처리 중단이 발생하지 않습니다(index 301~820 커밋).
3. **DB 복구 감지 및 Reconciliation (30초 이내)**:
   - backoff 주기 헬스체크(`SELECT 1`)가 성공하면 상태를 `RECONCILING`으로 전환합니다.
   - DB에서 `batch_sync_checkpoint.last_log_index`(300)를 조회합니다.
   - `RaftLogManager`에서 301부터 커밋 구간을 500건 단위로 판독하여, 청크마다 단일 트랜잭션으로 해당 `log_index` 구간 삭제 후 INSERT와 체크포인트 갱신을 커밋하고 압축 하한선을 전진합니다.
   - 마지막 청크(820)까지 반영되면 `SYNC_CHECKPOINT(820)`를 제안하여 전 노드 압축 하한선을 동기화하고 상태를 `NORMAL`로 복귀합니다.
4. **동기화 중 리더 교체 시 재개**:
   - `WriteBehindSynchronizer`는 리더에서만 활성화되며, Follower로 강등되면 즉시 중단합니다.
   - 신규 리더의 `WriteBehindSynchronizer`는 승격 시 DB 체크포인트를 조회하여 해당 지점부터 재개합니다. 구 리더의 미완료 트랜잭션과 구간이 겹쳐도 구간 삭제 후 삽입과 체크포인트 단조 증가 갱신으로 중복 없이 반영됩니다.

#### 5. Scenario 5: 네트워크 분할(Split-Brain 방지) 및 클러스터 재수렴 흐름

##### 1) 개요 및 사전 조건
- **목적**: 네트워크 단절로 클러스터가 소수파(1대)와 다수파(2대)로 분할될 때, 소수파의 쓰기·인출·조회를 모두 차단하여 이중 마스터에 의한 중복 디스패치를 방지(`QAS-03`)하고, 네트워크 복구 후 단일 리더 체제로 로그와 FSM 상태를 수렴시키는 절차를 정의합니다.
- **사전 조건**: 3개 노드 클러스터(term=1, commitIndex=400)에서 **Partition A {Node 1 (Leader)}** 와 **Partition B {Node 2, Node 3 (Follower)}** 로 네트워크 분할이 발생합니다. Node 1의 `BatchLauncher`는 `exec-301`을 추적 중입니다.
- **설계 포인트**:
  - 큐 인출을 포함한 모든 상태 변경이 커밋 후 apply되므로, 소수파 리더는 작업을 인출·디스패치할 수 없습니다.
  - 소수파 리더는 Check-Quorum으로 Election Timeout 이내에 스스로 강등합니다. 강등 전의 짧은 구간에도 과반 응답이 없어 커밋이 불가능하므로, 상태 변경과 이에 근거한 디스패치가 발생하지 않습니다.
  - 고립 노드는 PreVote로 불필요한 term 증가를 억제하여, 네트워크 복구 시 정상 리더를 교란하지 않습니다.

##### 2) 참여 컴포넌트 (Lifeline)

| 구분 | 참여 컴포넌트 (Lifeline) | 분류 / 계층 매핑 | 역할 및 주요 책임 |
| :--- | :--- | :--- | :--- |
| **소수파 클라이언트** | `Node 1 Scheduler Core / BatchLauncher` | Application (`com.sds.batchservice.scheduler`) | 분할 중 요청이 TIMEOUT/NOT_LEADER로 거부됨을 수신 |
| **소수파 노드** | `Node 1 (Partition A) ConsensusEngine` | Raft Core [구 Leader] | Quorum 미달로 커밋 불가, Check-Quorum 강등, PreVote로 term 유지 |
| **다수파 리더** | `Node 2 (Partition B) ConsensusEngine` | Raft Core [신규 Leader] | PreVote/RequestVote로 승격, `NO_OP`·멤버십·신규 작업 커밋 |
| **다수파 피어** | `Node 3 (Partition B) ConsensusEngine` | Raft Core [Follower] | 투표 및 복제 참여 |
| **다수파 클라이언트** | `Node 2 Scheduler Core / BatchLauncher` | Application (`com.sds.batchservice.scheduler`) | 신규 리더 체제에서 정상 요청 수행 |

##### 3) 단계별 제어 흐름
1. **네트워크 분할**: Partition A와 Partition B 간 모든 P2P TCP 통신이 단절됩니다.
2. **소수파 쓰기·인출·조회 차단 (Split-Brain 방지)**:
   - Node 1은 `QUEUE_DEQUEUE` 요청을 index=401(term=1)로 WAL에 기록하고 복제를 시도하지만 과반수 응답을 받지 못합니다. 엔트리는 **커밋·apply되지 않으므로 작업이 인출되지 않고**, 2,000ms 후 `TIMEOUT`을 반환합니다.
   - Election Timeout 동안 과반수 응답이 없으면 Check-Quorum에 의해 Follower로 강등되며, 이후 요청에는 `NOT_LEADER`를 반환합니다. 소수파 노드의 로컬 FSM 조회는 분할 이전에 커밋된 상태만 반환하며, 락 획득·인출 명령이 커밋되지 않으므로 이를 근거로 한 판정과 디스패치는 진행되지 않습니다(불변식 7).
   - Node 1이 추적하던 `exec-301`은 lease 갱신이 불가능해지며, 다수파 리더가 node-1을 DEAD로 판정한 후 Scenario 2의 고립 작업 판정 절차(Execution Target 상태 조회)로 중복 없이 처리합니다.
3. **다수파 신규 리더 선출 및 정상 쓰기**:
   - Node 2는 Election Timeout 만료 후 PreVote와 `RequestVote(term=2, lastLogIndex=400, lastLogTerm=1)`로 Node 3의 표를 얻어 리더로 승격합니다.
   - `NO_OP`(401)과 `MEMBER_STATUS(node-1, DEAD)`(402)를 커밋한 후, 신규 작업(`Job_501`, index=403)을 Node 3과 합의하여 커밋합니다.
4. **고립 노드의 term 인플레이션 방지**: Node 1은 Follower 상태에서 Election Timeout이 만료되어도 PreVote 과반을 얻지 못하므로 `currentTerm=1`을 유지합니다.
5. **네트워크 복구 및 클러스터 재수렴**:
   - Node 2가 Node 1에 `AppendEntries(term=2, prevLogIndex=400, prevLogTerm=1, entries=[401..403], leaderCommit=403)`를 전송합니다.
   - Node 1은 상위 term(2)을 `fsync`하고, `prevLog(400, term 1)` 일치를 확인한 뒤 index 401에서 term 충돌(1 ≠ 2)을 발견하여 **401 이후를 절단**합니다(공통 런타임 규약 4의 Flowchart 4, 케이스 5). 이 미커밋 엔트리의 클라이언트는 이미 `TIMEOUT`을 받았으므로 확인 응답이 유실되지 않습니다.
   - Node 1은 401~403을 append·apply하여 리더와 동일 상태로 수렴하고, 리더는 `MEMBER_STATUS(node-1, ALIVE)`를 커밋합니다.
