#### 1. 공통 헬퍼

```java
/** 서비스 가능한(NO_OP 커밋 완료) 리더가 선출될 때까지 최대 5초 대기 */
static RaftNode awaitLeader(VirtualCluster cluster) {
    return await().atMost(5, TimeUnit.SECONDS).until(cluster::getLeaderNode, java.util.Objects::nonNull);
}

/** 모든 실행 노드의 commitIndex·lastApplied·로그 term이 일치하는지 검증 (클러스터 재수렴) */
static void assertLogsConverged(VirtualCluster cluster) {
    List<RaftNode> nodes = cluster.runningNodes();
    long commit = nodes.get(0).getCommitIndex();
    for (RaftNode n : nodes) {
        assertThat(n.getCommitIndex()).isEqualTo(commit);
        assertThat(n.getLastApplied()).isEqualTo(commit);
        for (long i = 1; i <= commit; i++) {
            assertThat(n.getRaftLog().termAt(i)).as(n.getNodeId() + " term@" + i)
                    .isEqualTo(nodes.get(0).getRaftLog().termAt(i));
        }
    }
}
```

### 7.2.1 TC-QAS-01: DAG 오케스트레이션 동시성 및 상태 정합성 검증

* **대응 요구사항**: `QAS-01 [일관성]`, `FR-01`, `NR-02`, `DD-02`
* **테스트 목적**: 3개 노드 클러스터에서 단일 DAG 워크플로우에 대해 동시 100건의 상태 전이 요청이 3개 노드로 분산 유입될 때, Raft FSM 기반 분산 락(FIFO 대기열, fenceToken)으로 원자적 전이가 수행되고 후행 작업이 정확히 1회만 발화하는지 검증합니다.
* **사전 조건**: 3개 가상 노드 클러스터가 기동되어 리더가 선출됨. `DagStateManager`에 선행 Task A(COMPLETED), 후행 Task B(READY)가 로드됨.
* **테스트 절차**:
  1. 100개 스레드를 생성하고 `CountDownLatch`로 동시 출발 대기. 요청 `i`는 `node-(i % 3 + 1)`의 `DistributedLockExecutor`를 사용 (팔로워 노드 요청은 리더로 자동 전달).
  2. 100개 스레드가 동시에 `execute("dag-job-workflow-001", "req-i", ...)`로 `Task B` 상태 전이를 요청.
  3. 락 획득 건수, 후행 작업 실제 발화 횟수, 임계 구역 수행 시간, 전체 처리 시간을 계측.
  4. 종료 후 3개 노드 FSM 모두에서 락이 해제되었는지 확인.
* **계측 기준**: QAS-01의 "개별 상태 판정(임계 구역) 지연"은 락 획득 후 임계 구역 내 판정 수행 시간으로 측정합니다. 락 대기 시간을 포함하면 100건이 순차 직렬화되는 상호 배제 특성상 평균 대기가 전체 시간의 절반에 수렴하므로, 대기를 포함한 처리 성능은 "전체 100건 1초 이내"로 검증합니다.
* **핵심 테스트 코드 (발췌)**:

```java
lockExecutor.execute("dag-job-workflow-001", "req-" + requestId, () -> {
    long csStart = System.nanoTime();
    acquiredCount.incrementAndGet();
    if (dagStateManager.transitionToRunning("task-B")) {

    }

// ...

await().atMost(2, TimeUnit.SECONDS).untilAsserted(() -> cluster.runningNodes().forEach(n ->
        assertThat(n.getStateMachine().getLock().get("dag-job-workflow-001")).isNull()));
```

### 7.2.2 TC-QAS-02: 분산 큐 피크 타임 작업 인출 성능 검증

* **대응 요구사항**: `QAS-02 [성능]`, `FR-02`, `NR-02`, `DD-03`
* **테스트 목적**: 분산 큐에 적재된 200건의 대기열에 대해 3개 노드의 12개 워커 스레드(노드당 4개)가 동시 인출할 때, 모든 인출이 과반수 커밋 후 FSM apply 결과로 반환되면서도(Group Commit) 0.5초 이내에 중복·유실 없이 완료되는지 검증합니다.
* **사전 조건**: 리더를 통해 고유 ID를 가진 200건(`TASK-BATCH-1` ~ `200`)을 적재하고, 3개 노드 FSM 모두 대기열 200건이 반영된 상태.
* **테스트 절차**:
  1. 12개 워커 스레드를 기동 (`node-1` ~ `node-3`의 `DistributedQueueService`에 4개씩 할당).
  2. 각 워커가 `poll(50, MILLISECONDS)`를 반복 호출하여 대기열이 빌 때까지 인출.
  3. 인출 작업 ID의 유일성(Set), 인출 성공 건수(중복 검출), 개별 인출 지연과 전체 소요 시간을 계측.
* **핵심 테스트 코드 (발췌)**:
```java
// ArchitectureVerificationTest.testQAS02_DistributedQueuePerformance
// ... 리더에 TASK-BATCH-1 ~ 200 적재 후 3개 노드 FSM 반영 대기
long startAll = System.currentTimeMillis();
for (int w = 0; w < workerCount; w++) {
    final DistributedQueueService queue = queues.get(w % queues.size()); // 노드당 4개 워커
    workers.submit(() -> {
        while (!Thread.currentThread().isInterrupted() && completeLatch.getCount() > 0) {
            long fetchStart = System.currentTimeMillis();
            try {
                String task = queue.poll(50, TimeUnit.MILLISECONDS);
                if (task != null) {
                    fetchLatencies.add(System.currentTimeMillis() - fetchStart);
                    dequeuedTasks.add(task);
                    completeLatch.countDown();
                }
            } catch (InterruptedException e) {
                return;
            } catch (RuntimeException e) {
                log.warn("poll failed: {}", e.toString());
            }
        }
    });
}
boolean allDequeued = completeLatch.await(1, TimeUnit.SECONDS);
long totalElapsed = System.currentTimeMillis() - startAll;
// ... (평균·최대 인출 지연 계산)
assertThat(allDequeued).isTrue();
assertThat(dequeuedTasks).hasSize(taskCount);
assertThat(fetchLatencies).hasSize(taskCount); // 중복 인출 0건
assertThat(avg).isLessThanOrEqualTo(20.0);
assertThat(max).isLessThanOrEqualTo(50L);
assertThat(totalElapsed).isLessThanOrEqualTo(500L);
```

### 7.2.3 TC-QAS-03: Split-Brain 네트워크 분할 시 단일 리더 보장 검증

* **대응 요구사항**: `QAS-03 [신뢰성]`, `FR-04`, `NR-02`, `DD-01`, `DD-03`
* **테스트 목적**: 5.3.2 Scenario 5에 따라 **현재 리더**를 소수파(1대)로 격리했을 때, 소수파에서는 커밋·인출이 불가능하고 Check-Quorum으로 구 리더가 강등되며, 다수파(2대)가 신규 리더를 선출해 정상 쓰기를 수행하고, 네트워크 복구 후 단일 리더와 동일 로그로 재수렴하는지 검증합니다.
* **사전 조건**: 3개 노드가 정상 구동 중이며, 리더를 통해 `JOB-PARTITION` 1건이 적재되어 3개 노드 FSM에 반영된 상태.
* **테스트 절차**:
  1. `VirtualNetworkRouter.isolateNode(oldLeaderId)`로 구 리더를 격리 (Partition A {구 리더} / Partition B {나머지 2대}).
  2. 구 리더 노드에서 `pollLease()`를 호출하여 `ClusterUnavailableException`(과반수 미달로 커밋 불가)을 확인.
  3. 다수파에서 신규 리더가 선출될 때까지 대기한 후, 활성 리더 수와 구 리더의 강등 여부, 대기열 보존(`JOB-PARTITION` 미인출)을 검증.
  4. 신규 리더에 `JOB-301`을 적재한 후 네트워크를 복구하고, 단일 리더·로그 일치·구 리더 FSM 수렴을 검증.
* **핵심 테스트 코드 (발췌)**:
```java
// ArchitectureVerificationTest.testQAS03_SplitBrainSingleLeader
// ... 리더를 통해 JOB-PARTITION 적재 후 3개 노드 반영 대기
// 리더를 소수파로 격리 (Partition A {old leader} / Partition B {나머지 2대})
cluster.getNetworkRouter().isolateNode(oldLeaderId);
assertThatThrownBy(() -> cluster.getQueueService(oldLeaderId).pollLease())
        .isInstanceOf(ClusterUnavailableException.class); // 소수파 인출 불가

RaftNode newLeader = await().atMost(5, TimeUnit.SECONDS).until(cluster::getLeaderNode,
        l -> l != null && !l.getNodeId().equals(oldLeaderId));
int totalActiveLeaders = cluster.getActiveLeaderCount();
boolean oldLeaderStillLeader = oldLeader.isLeader();
// ...
assertThat(oldLeaderStillLeader).isFalse();          // Check-Quorum 강등
assertThat(totalActiveLeaders).isLessThanOrEqualTo(1);
assertThat(newLeader.getStateMachine().getQueue().waitingSnapshot()).containsExactly("JOB-PARTITION");

// 다수파 정상 쓰기 후 네트워크 복구 → 재수렴
assertThat(cluster.getQueueService(newLeader.getNodeId()).offer("JOB-301")).isTrue();
cluster.getNetworkRouter().reconnectNode(oldLeaderId);
await().atMost(5, TimeUnit.SECONDS).untilAsserted(() -> {
    assertThat(cluster.getActiveLeaderCount()).isEqualTo(1);
    assertLogsConverged(cluster);
});
assertThat(oldLeader.getStateMachine().getQueue().waitingSnapshot()).containsExactly("JOB-PARTITION", "JOB-301");
```

### 7.2.4 TC-QAS-04: 일반 멤버 노드 장애 감지 및 3초 이내 멤버십 자가 치유 검증

* **대응 요구사항**: `QAS-04 [운용성/가용성]`, `FR-04`, `NR-04`, `DD-01`
* **테스트 목적**: 5.3.2 Scenario 3에 따라 Follower 노드가 비정상 종료되었을 때, 리더가 **팔로워별 마지막 AppendResponse 수신 시각**으로 2초 이내에 장애를 감지하고 `MEMBER_STATUS(DEAD)`를 과반수 커밋하여 3초 이내에 활성 멤버십에서 제외하며, 잔여 노드에도 동기화되고 정상 노드는 오탐으로 제외되지 않는지 검증합니다.
* **사전 조건**: 3개 노드가 정상 구동 중이며 리더의 활성 멤버십이 3개 노드인 상태.

  4. 정상 팔로워의 FSM에도 멤버십 변경이 반영되는지(잔여 노드 동기화) 확인.
* **핵심 테스트 코드 (발췌)**:
```java

        !cluster.getNode(healthy).getActiveMembers().contains(crashed)); // 잔여 노드 동기화
```

### 7.2.6 TC-QAS-06: 비정상 종료 시 저널 기반 미완료 작업 복구 검증

* **대응 요구사항**: `QAS-06 [신뢰성]`, `FR-03`, `DD-03`, `DD-04`
* **테스트 목적**: 5.3.2 Scenario 2의 4~5단계에 따라 작업을 추적하던 리더 노드가 크래시되었을 때, 신규 리더의 `RecoveryCoordinator`가 10초 이내에 고립 작업을 식별하고 **Execution Target 상태에 따라** 재적재·추적 인수·완료 처리를 로그 명령으로 커밋하며, 생존 노드가 추적 중인 작업은 조치하지 않고(중복 실행 방지), 구 추적자의 뒤늦은 보고는 펜싱으로 거부되는지 검증합니다.

  2. 신규 리더의 복구 조치(락 회수 제외) 5건이 커밋될 때까지 계측.
  3. 신규 리더 FSM에서 결과 검증: `JOB-1~3` 대기열 재적재, `JOB-4` 신규 리더로 추적 인수(재실행 없음), `JOB-5` 완료 확정, `JOB-11` 원 추적 노드 유지.

* **판정 매트릭스**:

| 작업 | 추적 노드 | Target 상태 | 기대 조치 | 기대 FSM 상태 |
| :--- | :--- | :--- | :--- | :--- |

| JOB-4 | 구 리더 (DEAD) | RUNNING | `ADOPTED` | in-flight, worker = 신규 리더, 신규 leaseToken |
| JOB-5 | 구 리더 (DEAD) | COMPLETED | `COMPLETED` | 저널 COMPLETED, in-flight 제거 |
| JOB-6 ~ 10 | - | - | 조치 없음 | 저널 COMPLETED |
| JOB-11 | 팔로워 (ALIVE) | - | **조치 없음** | in-flight, worker = 원 팔로워 |

### 7.2.7 TC-QAS-07: 노드당 자원(Heap 메모리/CPU) 점유율 최적화 검증

* **대응 요구사항**: `QAS-07 [효율성]`, `NR-06`, `DD-06`
* **테스트 목적**: 분산 엔진 1개 노드(RaftNode, WAL, Multi-FSM, Write-Behind, RecoveryCoordinator)를 기동하고 작업 1,000건을 적재한 뒤 백그라운드 합의 루프를 가동했을 때, 추가 JVM Heap 점유가 50MB 이하이며 GC 누적 시간이 1초 이내인지 검증합니다.
* **사전 조건**: 테스트 시작 시 `System.gc()` 수행 후 초기 Heap 사용량과 GC 누적 시간을 기록.
* **테스트 절차**:
  1. 엔진 기동 전 Heap 사용량($M_0$)과 GC 누적 시간($G_0$) 측정.
  2. 1노드 가상 클러스터 기동, 리더 선출 후 작업 1,000건 적재, 5초간 합의 루프 가동.
  3. `System.gc()` 후 Heap 사용량($M_1$)과 GC 누적 시간($G_1$) 측정.
  4. $M_1 - M_0$ 및 테스트 구간 GC 시간 $G_1 - G_0$ 판정.
* **측정 한계**: 단일 JVM에서 테스트 러너·Spring 미사용 상태로 측정하므로 GC 시점에 따라 값의 편차가 크며(0MB 또는 음수 가능), 실제 노드당 점유는 4단계 TC-K8S-07(엔진 비활성 기준선 Pod 대비 Heap·컨테이너 메모리 비교, 7.2.13)로 보완 검증합니다.
* **핵심 테스트 코드 (발췌)**:
```java
// ArchitectureVerificationTest.testQAS07_ResourceFootprintOptimization

System.gc();
Thread.sleep(500);
long initialHeapUsed = memoryBean.getHeapMemoryUsage().getUsed();
long gcTimeBefore = totalGcTime();
// ... 1노드 VirtualCluster 기동, 리더 선출 후 작업 1,000건 적재
Thread.sleep(5000); // 백그라운드 합의 루프 가동

System.gc();
Thread.sleep(500);
long additionalHeapMB = (memoryBean.getHeapMemoryUsage().getUsed() - initialHeapUsed) / (1024 * 1024);
long gcPause = totalGcTime() - gcTimeBefore;
// ...
assertThat(additionalHeapMB).isLessThanOrEqualTo(50L);
assertThat(gcPause).isLessThanOrEqualTo(1000L);
```

### 7.2.8 TC-QAS-08: 외부 미들웨어 독립적 환경 자동 구성 및 배포 검증

### 7.2.9 TC-QAS-09: 메타 DB 장애 중 무중단 운영 및 정합성 복원 검증

* **대응 요구사항**: `QAS-09 [가용성/내구성]`, `NR-09`, `DD-01`, `DD-02`, `DD-03`, `DD-04`, `DD-05`
* **테스트 목적**: 5.3.2 Scenario 4에 따라 메타 DB 연결이 끊긴 상태에서도 분산 락·큐가 중단 없이(실패 0건) 동작하고 노드 Readiness가 유지되며, DB 복구 후 `WriteBehindSynchronizer`가 DB 체크포인트로부터 30초 이내에 미반영 이력을 유실·중복 없이 동기화하는지 검증합니다.
* **사전 조건**: 3개 노드 클러스터 기동 및 리더 선출, 리더의 Write-Behind가 초기 동기화(`NORMAL`)를 완료한 상태.
* **테스트 절차**:
  1. `MockDatabaseProxy.disconnect()`로 DB 연결 차단.
  2. 3개 노드에 분산하여 50건의 `락 획득 → 적재 → 인출 → ACK → 락 해제`를 수행하고 성공 건수 계측.
  3. Write-Behind 상태가 `DB_DOWN`으로 전환되고, 모든 노드 Readiness가 유지되며, 미동기화 이력이 누적(50건 × 5 명령 이상)되었는지 확인.
  4. `MockDatabaseProxy.reconnect()` 후 `isFullySynchronized()`까지 소요 시간 계측.
  5. 미동기화 0건, DB 반영 건수, DB 체크포인트와 동기화 기준점 일치 여부 검증.
* **핵심 테스트 코드 (발췌)**:
```java
// ArchitectureVerificationTest.testQAS09_DatabaseOutageResilience
dbProxy.disconnect();
int taskCount = 50;
AtomicInteger successfulOperations = new AtomicInteger();
List<String> ids = cluster.getNodeIds();
for (int i = 0; i < taskCount; i++) {
    final int opId = i;
    String nodeId = ids.get(i % ids.size());
    DistributedQueueService queue = cluster.getQueueService(nodeId);
    cluster.getLockExecutor(nodeId).execute("db-down-lock", "op-" + opId, () -> {
        queue.offer("TASK-OFFLINE-" + opId);
        QueueLease lease = queue.pollLease();
        if (lease != null && queue.ack(lease)) {
            successfulOperations.incrementAndGet();
        }
        return null;
    });
}
WriteBehindSynchronizer sync = cluster.getWriteBehindSynchronizer();
await().atMost(2, TimeUnit.SECONDS).until(() -> sync.getState() == WriteBehindSynchronizer.State.DB_DOWN);
assertThat(successfulOperations.get()).isEqualTo(taskCount);          // 중단 시간 0초
assertThat(cluster.runningNodes()).allMatch(RaftNode::isReady);        // Readiness 영향 없음
assertThat(sync.getUnsyncedRecordCount()).isGreaterThanOrEqualTo(taskCount * 5L);

long tDbRecovered = System.currentTimeMillis();
dbProxy.reconnect();
await().atMost(30, TimeUnit.SECONDS).until(sync::isFullySynchronized);
long syncElapsed = System.currentTimeMillis() - tDbRecovered;
// ...
assertThat(syncElapsed).isLessThanOrEqualTo(30_000L);
assertThat(sync.getUnsyncedRecordCount()).isZero();
assertThat(dbProxy.countRecords()).isGreaterThanOrEqualTo(taskCount * 5L);
assertThat(dbProxy.readCheckpoint("virtual-cluster")).isEqualTo(sync.getCheckpoint());
```
* **QAS-09 대응**:

| 코드 | QAS-09 대응 |
| :--- | :--- |
| `dbProxy.disconnect()` | 자극: 메타 DB 접속 불가 장애 |
| 락 획득·적재·인출·ACK 50건 성공 = `taskCount`, 전 노드 `isReady` | 응답 측정 1: 분산 락·큐 처리 중단 시간 0초 |
| `dbProxy.reconnect()` 후 `syncElapsed` ≤ `30_000L` | 응답 측정 2: DB 복구 후 미반영 이력 동기화 30초 이내 |
| 미동기화 `0`, 반영 건수 ≥ 250, DB 체크포인트 = 동기화 기준점 | 응답 측정 3: 동기화 누락·유실 0건 |

* **직접 실행 및 검증 방법**:
  - **실행 명령**: `./gradlew test --tests "com.sds.batchservice.cluster.ArchitectureVerificationTest.testQAS09_DatabaseOutageResilience"`
  - **콘솔 로그 확인** (측정 예시):
    ```text
    [WARN] MockDatabaseProxy: Connection severed (Simulating DB Outage).
    [WARN] [node-1] Meta DB unavailable → DB_DOWN (checkpoint=1): Database connection unavailable (Connection refused)
    [INFO] MockDatabaseProxy: Connection restored (DB is now ONLINE).
    [INFO] [node-1] Write-Behind activated from DB checkpoint last_log_index=1.
    [INFO] [node-1] Write-Behind synchronized up to index 252 → NORMAL.
    [INFO] TC-QAS-09: 252 records synchronized in 904ms after DB recovery
    ```
    - 복구 감지 지연은 DB 재시도 backoff(1s → 2s → 4s → 8s → 10s 상한)에 따라 달라지며, 최악의 경우 10초 감지 + 동기화로 30초 이내를 보장

#### 4. TC-K8S-01 임계 구역 구성에 따른 반복 측정

TC-K8S-01은 BatchService 사용 형태에 맞춰 임계 구역에서 메타 DB를 조회·갱신하므로, 엔진의 락 직렬화 비용과 DB 왕복 비용이 함께 측정됩니다. 두 비용을 구분하기 위해 임계 구역의 외부 I/O를 제외한 TC-K8S-01B를 추가하고, 워밍업 단계 도입 전에 신규 배포 직후부터 3회 연속 측정했습니다 (minikube 4 vCPU / 6GiB).

| 회차 | TC-K8S-01 (DB 포함) 전체 / 임계 구역 평균 | TC-K8S-01B (DB 제외) 전체 / 임계 구역 평균 | 판정 |
| :--- | :--- | :--- | :--- |
| 1 (신규 배포 직후) | 3,398ms / 16.13ms | 1,322ms / 0.002ms | 두 방식 모두 1초 초과 |
| 2 | 881ms / 2.09ms | 712ms / 0.001ms | 두 방식 모두 통과 |
| 3 | 947ms / 1.89ms | 806ms / 0.001ms | 두 방식 모두 통과 |

- 두 방식 모두 상호 배제는 유지되었습니다 (발화 1회, 임계 구역 중첩 0건).
- 워밍업 이후 엔진의 락 직렬화 비용은 요청당 약 7~8ms이며, 락 획득·해제 커밋, 팔로워 요청의 리더 전달, PVC `fsync`가 포함됩니다. DB 왕복 비용은 100건 기준 약 140~170ms입니다.
- 1회차는 DB를 제외한 방식도 기준을 초과하므로, 원인은 DB가 아니라 신규 배포 직후의 JIT·커넥션 초기화입니다. QAS-01의 환경 조건은 가동 중인 시스템(평시 피크 타임)이므로 측정 전 워밍업 단계를 테스트에 추가했습니다 (7.1.6-4).

#### 5. 결과 해석 시 유의사항

- 측정값은 minikube 싱글노드(hostpath PVC, 공유 vCPU) 기준입니다. 싱글노드에서 재현되지 않는 항목과 운영 규격 환경의 검증 계획은 7.1.5를 따릅니다.
- 드라이버가 조회 주기로 관측하는 소요 시간은 실제보다 최대 한 조회 주기만큼 크게 기록될 수 있습니다. TC별 조회 주기는 7.1.6-4를 참조합니다.
- 크래시 주입은 Chaos Mesh `container-kill`(SIGKILL)이며, TC-K8S-10·11의 Pod 삭제·롤링 업데이트는 SIGTERM 정상 종료를 수반합니다.
