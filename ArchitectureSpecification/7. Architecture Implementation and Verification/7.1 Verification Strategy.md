본 문서는 분산 배치 엔진(BatchService)의 경량 분산 코디네이션 엔진(`batch-clustering-engine`)이 3. Architecture Driver에서 정의된 품질 속성 시나리오(QAS-01 ~ QAS-09)와 4. Top Level Design의 아키텍처 설계 의사결정(DD-01 ~ DD-07), 그리고 5.3.2 Scenario View의 안전성 불변식을 충족하는지 객관적으로 입증하기 위한 검증 전략을 정의합니다. 상세 테스트 케이스는 7.2절을 참조합니다.

### 7.1.1 검증 개요 및 목표

본 아키텍처 검증의 핵심 목표는 외부 분산 미들웨어(Zookeeper, Redis, Hazelcast 등) 없이 표준 Java 런타임 위에 In-Process 라이브러리(DD-06)로 구현된 다음 메커니즘이 비기능 요구사항(일관성, 성능, 신뢰성, 가용성, 효율성, 이식성, 내구성)을 충족하는지 사전에 확인하는 것입니다.

| 설계 결정 | 검증 대상 구현 | 주요 검증 관점 |
| :--- | :--- | :--- |
| DD-01 Socket P2P Raft | `RaftNode`, `SocketNetworkTransport` | PreVote/RequestVote 선출, 로그 최신성 투표, Check-Quorum 강등, 멤버십 자가 치유, Split-Brain 방지 |
| DD-02 Raft FSM 분산 락 | `LockStateMachine`, `DistributedLockExecutor` | 상호 배제, FIFO 대기열 승격, lease 갱신·만료, fenceToken 펜싱, AS-IS API 호환(스레드 단위 소유, 무기한 대기, 재진입) |
| DD-03 Raft FSM 분산 큐 | `QueueStateMachine`, `DistributedQueueService` | 커밋 후 인출, 중복·유실 0건, in-flight lease·ACK, Group Commit 성능 |
| DD-04 분산 저널링 | `JournalStateMachine`, `TaskJournalService`, `RecoveryCoordinator` | 고립 작업 판정, Execution Target 상태 기반 재적재·인수·완료, 구 보고 거부 |
| DD-05 로컬 WAL + Write-Behind | `RaftLogManager`, `WriteBehindSynchronizer`, `JdbcDatabaseStorage` | fsync WAL 복원, DB 장애 중 무중단, DB 체크포인트 기반 멱등 Reconciliation |
| DD-06 Embedded Library | `BatchClusteringAutoConfiguration`, `BatchClusterProperties` | 외부 프로세스 없는 부트스트랩, 자원 점유, 설정 누락 시 Fail-fast |
| DD-07 StatefulSet | 가상 클러스터 크래시/재기동 시뮬레이션, K8s StatefulSet·PVC 배포 (4단계) | 동일 식별자·WAL 디렉터리로 재기동 후 재합류, Pod 재생성·롤링 업데이트 중 Quorum 유지 및 작업 무유실 |

1~3단계 검증은 개발자가 별도의 외부 인프라 서버를 구축하지 않고도 로컬 개발 환경에서 즉시 실행하고 판정할 수 있도록 표준 테스트 프레임워크(JUnit 5, AssertJ, Awaitility)와 Gradle Wrapper를 기반으로 구성합니다. 4단계는 로컬 가상 클러스터가 재현하지 않는 실제 TCP 네트워크, PVC 디스크, Pod 생명주기를 minikube 싱글노드 Kubernetes에서 검증합니다(7.1.6).

#### 검증 원칙
1. **실제 합의 경로 검증**: 가상 클러스터의 각 노드는 WAL 디렉터리, Multi-FSM, 합의 엔진을 **독립적으로** 보유하며, 상태를 공유하거나 리더를 강제 지정하지 않습니다. 모든 상태 변경은 과반수 커밋 후 FSM apply 결과로만 확인합니다.
2. **명세 임계값 준수**: 테스트 단언문은 3.2 QAS의 응답 측정 기준(시간, 오류 건수)을 완화 없이 그대로 사용합니다.
3. **시나리오 추적성**: 각 테스트 케이스는 5.3.2 Scenario의 측정 구간(시작 → 종료 지점)과 1:1로 대응합니다 (7.2.0 추적표).
4. **결함 회귀 방지**: 아키텍처 설계 검토에서 식별된 결함은 별도 회귀 테스트(`RaftSafetyTest`)로 고정합니다.

### 7.1.2 단계별 검증 전략

검증 범위와 특성에 따라 테스트를 4단계로 분류하여 수행합니다.

![[7.1.2 Verification Stages.svg]]

1. **1단계: 동시성 및 구성 요소 검증 (Concurrency & Component Testing)**
   - 멀티스레드 환경(`ExecutorService`, `CountDownLatch`)에서 다수의 스레드가 3개 노드의 분산 락·분산 큐 API에 동시에 접근할 때, 팔로워 노드 요청의 리더 전달, FIFO 락 승격, 커밋 후 인출이 유지되는지 검증합니다.
   - 임계 구역 판정 시간(평균 10ms 이하), 100건 전체 처리(1초 이내), 개별 인출 지연(평균 20ms·최대 50ms 이하), 200건 전체 인출(0.5초 이내)을 계측합니다.
   - Write-Behind 대상 JDBC 저장소는 인메모리 H2로 트랜잭션 원자성과 멱등성을 단위 검증합니다.

2. **2단계: 가상 클러스터 기반 장애 시뮬레이션 검증 (Virtual Cluster & Fault Simulation Testing)**
   - 단일 JVM 프로세스 내에서 3개의 가상 노드를 구동하고, 프로세스 크래시(`crash`), 동일 WAL로 재기동(`restart`), 네트워크 격리(`isolateNode`)를 주입하여 리더 선출, 페일오버, 로그 절단·재수렴 흐름을 재현합니다.
   - DB 장애 주입 저장소(`MockDatabaseProxy`)로 메타 DB 단절 중에도 합의·락·큐가 중단 없이 동작하고, 복구 후 DB 체크포인트 기준으로 동기화되는지 확인합니다.
   - Execution Target 상태 조회(`ExecutionStatusProvider`)를 Mock으로 대체하여 고립 작업의 재적재·추적 인수·완료 판정을 검증합니다.

3. **3단계: 시스템 자원 및 배포 독립성 검증 (Resource & Packaging Testing)**
   - Java 표준 `MemoryMXBean` 및 `GarbageCollectorMXBean`으로 엔진 기동 전후의 Heap 증가량(50MB 이하)과 테스트 구간 GC 시간(1초 이내)을 측정합니다.
   - 가상 네트워크가 아닌 실제 `SocketNetworkTransport`(공유 토큰 핸드셰이크, 바이너리 프레임)와 로컬 WAL만으로 3개 노드가 부트스트랩되어 소켓 경로로 복제·커밋되는지 확인합니다.
   - Spring Boot 자동 구성(`BatchClusteringAutoConfiguration`)으로 수요처 애플리케이션에 주입되는 경로를 검증합니다.

4. **4단계: K8s 배포 통합 검증 (Kubernetes Deployment Integration Testing)**
   - 5.4.2 운영 매니페스트를 기준으로 minikube 싱글노드에 StatefulSet 3개 Pod를 배포하고, 엔진을 탑재한 테스트용 수요처 애플리케이션(Testbed)의 HTTP API로 QAS-01 ~ 09 시나리오를 실제 TCP·PVC·Pod 생명주기 위에서 재현합니다.
   - Chaos Mesh로 컨테이너 강제 종료(`container-kill`), 네트워크 분할(`partition`), 지연·패킷 손실(`netem`)을 주입하고, 메타 DB Pod 중단과 `ns-batch` 네임스페이스의 실제 Job 상태로 장애 복구 흐름을 검증합니다.
   - Pod 재생성 시 동일 PVC의 WAL 복원과 부하 중 롤링 업데이트의 Quorum 유지·작업 무유실(DD-07)을 추가로 검증합니다. 상세 테스트 케이스와 결과는 7.2.13을 참조합니다.

#### 장애 주입 의미
- **`crash(nodeId)`**: 스레드를 즉시 정지하고 종료 시점의 commitIndex 영속화를 생략합니다(평시 commitIndex는 1초 주기로 영속화). WAL 파일은 디스크에 유지되어 Pod 비정상 종료를 재현합니다.
- **`restart(nodeId)`**: 동일 WAL 디렉터리로 새 인스턴스를 기동하여 StatefulSet의 동일 식별자·PVC 재마운트(DD-07)를 재현합니다.
- **`isolateNode(nodeId)`**: 해당 노드가 보내거나 받는 모든 메시지를 드롭하여 1:2 네트워크 분할을 재현합니다. `reconnectNode(nodeId)`로 분할을 해소합니다.
- **`disconnect()` / `reconnect()`** (`MockDatabaseProxy`): 메타 DB 연결을 차단하여 체크포인트 조회·이력 반영에서 `SQLException`을 발생시키고, 연결 복구 후 Write-Behind가 DB 체크포인트부터 재동기화하는지 검증합니다.
- **`setClockOffset(nodeId, offsetMs)`**: 해당 노드의 시스템 시계에 오차를 주입하여, 리더 교체 시 노드 간 시계 차이가 lease 만료 판정에 영향을 주지 않는지 검증합니다 (`RaftSafetyTest`).

| 임계 구역 수행 시간 | TC-QAS-01 | 락 획득 후 판정 전후 시각 차이 | 이벤트 시각 기록 (ms 정수) | 폴링 영향 없음. 1ms 미만은 0으로 기록 |
| 전체 처리·인출 시간, 개별 인출 지연 | TC-QAS-01, 02 | 동시 출발 신호부터 완료 래치까지, 인출 호출 전후 시각 차이 | 이벤트 시각 기록 (ms) | 폴링 영향 없음. 워커의 `poll(50ms)` 대기는 대기열이 빈 뒤 종료 판정에만 사용 |
| Heap·GC | TC-QAS-07 | `System.gc()` 후 500ms 대기, 1,000건 적재 후 5초 가동 | 측정 전후 1회 | GC 시점에 따라 편차 (7.2.12-4) |

### 7.1.5 검증 범위의 한계 및 보완 계획

| 구분 | 로컬 검증의 한계 | 보완 결과 및 잔여 계획 |
| :--- | :--- | :--- |
| 네트워크 | 가상 라우터는 완전 차단만 재현하며, 실제 지연·패킷 손실·부분 단절은 재현하지 않음 | 4단계에서 Chaos Mesh `partition`·`netem`으로 실제 TCP 분할과 지연·손실을 검증 (TC-K8S-03, 12). 물리 스위치·다중 VM 간 네트워크는 운영 규격 스테이징에서 확인 |
| 디스크 내구성 | 테스트 WAL은 JUnit `@TempDir`(Linux `/tmp`, tmpfs)에 기록되어 디스크 fsync 지연이 측정값에 반영되지 않으며, PVC(블록 스토리지)의 fsync 지연과 다름 | 4단계에서 PVC(minikube hostpath) 위 fsync를 포함하여 TC-K8S-01·01B·02로 재측정. SSD 계열 StorageClass 기준 측정은 운영 규격 스테이징에서 수행 |
| 자원 점유 (TC-QAS-07) | 단일 JVM에서 GC 시점에 따라 Heap 측정 편차가 큼 | 4단계에서 엔진 비활성 기준선 Pod 대비 추가 Heap·컨테이너 메모리 비교 (TC-K8S-07). 장기 운영 누적(로그 압축 미구현)은 컨테이너 메트릭으로 관측 |
| 로그 압축 | Snapshot / InstallSnapshot / 로그 압축은 미구현으로 검증 대상에서 제외 (압축 하한선 관리만 구현) | 구현 후 장기 운영·재합류 시나리오 테스트 추가 |
| 전송 보안 | 공유 토큰 핸드셰이크만 검증하며 전송 구간 암호화(mTLS)는 검증하지 않음 | 서비스 메시(mTLS) 적용 환경에서 연결 검증 |
| Execution Target | 실행 상태 조회는 Mock 응답으로 검증 | 4단계에서 K8s Job API 기반 `ExecutionStatusProvider`와 RBAC로 실제 Job 상태 판정 검증 (TC-K8S-06) |
| CPU 오버헤드 (`NR-06`) | TC-QAS-07은 Heap·GC만 측정하며 추가 CPU 사용률(5% 미만)은 측정하지 않음 | 운영 환경 컨테이너 CPU 메트릭으로 엔진 활성 전후 비교 측정 (TC-K8S-07도 Heap·컨테이너 메모리만 측정) |
| 정상 종료·노드 수 변경 (`UC-04`, `UC-05`) | 비정상 종료(`crash`)와 동일 WAL 재기동만 재현하며, SIGTERM 정상 종료와 `RAFT_PEERS` 변경 재배포는 전용 테스트가 없음 | 4단계에서 SIGTERM 정상 종료를 수반하는 Pod 삭제·롤링 업데이트를 검증 (TC-K8S-10, 11). 노드 드레인과 `RAFT_PEERS` 변경 재배포는 운영 규격 스테이징에서 검증 |
| 수동 제어 (`UC-06`) | 우선 적재(`offerFirst`)와 강제 종료 경로는 전용 테스트가 없으며, 무효화된 소유권의 보고 거부(펜싱)만 TC-QAS-06에서 확인 | 수요처 관리 API 연동 통합 테스트 |
| StatefulSet 매니페스트 (`DD-07`) | Pod 재스케줄링·PVC 재마운트·`Parallel` 기동·PDB 동작은 가상 클러스터로 재현하지 않음 | 4단계에서 5.4.2 매니페스트 기반 `Parallel` 기동, Pod 재생성 후 동일 PVC 재마운트·재합류, 롤링 업데이트를 검증하고 이 과정에서 식별된 엔진 결함 5건을 수정 (TC-K8S-08, 10, 11, 7.2.13). 싱글노드이므로 `podAntiAffinity`, VM 장애, 노드 드레인 시 PDB 동작은 전용 노드 풀 3대 이상의 운영 규격 스테이징에서 검증 |

### 7.1.6 K8s 통합 검증 환경 및 실행 절차

4단계 검증은 `batch-clustering-e2e` 모듈로 수행합니다. 엔진은 Gradle Composite Build로 현재 소스를 그대로 참조하므로 별도 배포 없이 수정 사항이 검증에 반영됩니다.

#### 1. 실행 환경

| 호스트 | Multipass VM, Ubuntu 26.04 LTS (Linux 7.0.0-31-generic), 4 vCPU, 7.9GiB RAM, 스왑 4GiB |
| Kubernetes | minikube v1.39.0 (docker 드라이버, 싱글노드, 4 vCPU / 6GiB), Kubernetes v1.37.0, containerd 2.3.4 |
| 장애 주입 | Chaos Mesh 2.8.4 (Helm, containerd 런타임) |
| 메타 DB | PostgreSQL 16 (`postgres:16-alpine`, 1GiB PVC, 5.4.2-5 DDL 사전 적용) |

| 검증 드라이버 | JUnit 5, AssertJ, Awaitility, kubectl. 호스트에서 Pod별 NodePort(30080~30082)로 Testbed API를 호출 |

#### 3. 운영 매니페스트 대비 변경점 (overlay)

| 항목 | 5.4.2 (base) | minikube overlay | 사유 |
| :--- | :--- | :--- | :--- |
| `nodeSelector`, `tolerations`, `podAntiAffinity` | 전용 노드 풀, 호스트별 1개 강제 분산 | 제거 | 싱글노드에서 필수 anti-affinity를 유지하면 Pod 2개가 Pending |

#### 4. 계측 방법

- **서버 측 계측**: 지연 시간은 Testbed가 서버 시계로 기록하여 드라이버와의 HTTP 왕복 시간을 제외합니다. 싱글노드에서는 모든 Pod가 같은 커널 시계를 사용하므로 Pod 간 시각을 비교할 수 있습니다.
- **크래시 시점(T0)**: 드라이버가 20ms 주기로 대상 JVM에 요청하여, Chaos Mesh `container-kill` 적용 전 마지막 정상 응답 시각을 T0로 사용합니다. 장애 주입 리소스 반영 지연은 측정 구간에서 제외됩니다.
- **신규 배포 보장**: TC-K8S-08은 StatefulSet과 WAL PVC를 삭제한 뒤, minikube hostpath 프로비저너가 남길 수 있는 PV와 디렉터리를 정리하고 동기화 테이블을 비웁니다. 기동 직후 리더의 commitIndex가 10 이하인지 확인하여 이전 WAL을 재사용한 기동을 배제합니다.
- **장애 지속**: 크래시 후 재시작된 컨테이너가 복구 판정 전에 재합류하지 않도록, TC-K8S-06은 크래시 직후 대상 Pod를 나머지 Pod와 네트워크 분할합니다.
- **워밍업**: TC-K8S-01·01B는 측정 전 같은 경로로 동시 30건을 보내고 결과를 버립니다. QAS-01의 환경 조건은 가동 중인 시스템(평시 피크 타임)이며, 재배포 직후 JIT·커넥션 초기화 지연은 측정에서 제외합니다.
- **판정 기준**: 3.2 QAS 응답 측정 기준을 완화 없이 적용합니다.

**계측 주기와 측정 해상도**

드라이버는 Pod 상태를 NodePort로 주기적으로 조회하여 조건 충족 시각을 기록합니다. 기록값은 실제보다 최대 한 조회 주기(조회 응답 시간 포함)만큼 크게 기록될 수 있으며, 판정에서 이 오차를 보정하지 않습니다. 엔진 내부의 판정 주기는 5.3.2 공통 런타임 규약 6을 따릅니다.

| 계측 대상 | 대상 TC | 주기 / 타임아웃 | 측정값 영향 |
| :--- | :--- | :--- | :--- |
| 크래시 시점(T0) | TC-K8S-04, 05, 06 | 대상 JVM `/testbed/ping` 20ms 주기 조회 (응답 타임아웃 500ms) | T0는 실제 종료보다 최대 약 20ms 앞선 마지막 정상 응답 시각이므로, 소요 시간은 그만큼 크게 기록 |
| 멤버십 제외, 신규 리더 서비스 가능 | TC-K8S-04, 05 | 50ms 폴링 | 완료 시각이 최대 50ms 늦게 관측 |
| 분할 후 신규 리더, 고립 작업 복구 조치 | TC-K8S-03, 06 | 100ms 폴링 | 최대 100ms |
| Write-Behind `DB_DOWN` 전환, 동기화 완료 | TC-K8S-09 | 100ms 폴링 (평시 `NORMAL` 확인과 DB 체크포인트 일치는 200ms) | 동기화 시간이 최대 100ms 크게 기록 |
| 3개 Pod Ready 및 리더 확인 | TC-K8S-08 | 500ms 폴링 | 부트스트랩 시간이 최대 500ms 크게 기록 |
| Pod 재생성 후 Ready | TC-K8S-10 | 1초 폴링 (kubectl 조회) | 재생성 시간이 최대 1초 크게 기록 |
| 리더 수, 응답 가능 Pod 수, 리더 부재 시간, 활성 멤버 수 | TC-K8S-11, 12 | 250ms 간격 샘플링. 1회 샘플은 3개 Pod를 순차 조회 (Pod당 타임아웃 2초) | 리더 부재 시간은 샘플 간격(250ms + 조회 시간)만큼 크게 기록될 수 있음. 한 샘플 안의 Pod별 조회 시각이 달라 동시 시점 상태가 아니며, 샘플 사이의 짧은 상태 변화는 관측되지 않을 수 있음 |
| 적재 부하 | TC-K8S-11 | 100ms 간격 적재, 실패 시 100ms 후 다른 Pod로 재시도 (요청 타임아웃 6초) | 쓰기 공백 최대값에 재시도 대기와 요청 타임아웃이 포함 |
| 로그 수렴, Chaos Mesh 주입 완료, 메타 DB Pod 종료 | TC-K8S-03, 10, 11 등 | 200ms 폴링 | 판정 대상 시간이 아닌 사전·사후 조건 확인 |
| 클러스터 정상 상태 (사전 조건) | 전체 | 1초 폴링 | 측정 구간에 포함되지 않음 |
| 전체 처리 시간, 임계 구역, 개별 인출 지연 | TC-K8S-01, 01B, 02 | Testbed가 서버 시계로 이벤트 시각 직접 기록 | 폴링 영향 없음. TC-K8S-02 워커의 `poll` 대기 50ms는 대기열이 빈 뒤 종료 판정에만 사용 |

#### 5. 실행 방법

```bash
cd batch-clustering-e2e
# 사전 조건: docker, minikube, kubectl, helm, JDK 17 (JAVA_HOME)
./scripts/setup-minikube.sh

# TC-K8S 전체 실행 (TC-K8S-08이 StatefulSet·PVC·동기화 테이블을 초기화하고 신규 배포부터 측정)
./gradlew e2eTest

# 개별 실행 (예: 롤링 업데이트)
./gradlew e2eTest --tests "com.sds.batchservice.e2e.K8sArchitectureVerificationTest.tcK8s11_rollingUpdateUnderLoad"
```

- 결과 리포트: `build/reports/tests/e2eTest/index.html`
- 계측 로그: `TC-K8S-xx:` 접두어 라인 (Gradle 콘솔 또는 `build/test-results/e2eTest/TEST-*.xml`)
- 정리: `kubectl delete -k k8s/overlays/minikube` 또는 `minikube delete`
